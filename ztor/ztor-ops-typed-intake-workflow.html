Why the legend is a routing decision, not decoration

If all four types still walk the same six boxes, the labels add nothing. A type is only worth naming when it changes something: different required artifact, different approver, different SLA, different path. That is what each lane below encodes.

The type that was missing from the original is Campaign / Content — which is what the original diagram actually is. Without naming it, everything gets mislabelled "change request."

Boundary cases — how to classify when it's not obvious

CR vs NF

Ask: does the screen already exist? Changing a value, rule or label on an existing surface is CR. Anything that needs a new screen, new data model or new integration is NF — even if it "feels small."

BF vs CR

Ask: does it match the spec? If it behaves as specified but the spec is wrong, that's a CR, not a bug. Re-route it — never close a bug ticket as "working as intended" without opening the CR.

CM vs CR

A campaign that needs a new capability to run is two tickets, not one: a CM for the campaign and an NF/CR for the capability, with the CM blocked on it. This is where the 14-day SLA usually breaks.

Regional splits

Same campaign in HK + TW + SEA = one CM ticket with regional subtasks, not three tickets — otherwise IT sizes the same work three times and the reconciliation in Step 6 can't roll up.

Priority is a second axis — not a fifth type

Two axes, never merged

Type = what kind of work it is, and therefore which path it walks. Priority = how urgent it is, and therefore how fast that path runs. Every ticket carries both. "Urgent" is not a type, and a New Feature can be P1 without becoming a bug.

Guardrail

P0/P1 inflation

If everything is P1, nothing is. Only Ops Mgr or IT lead can set P0/P1 — requesters propose, triage decides. Review the P1 count monthly; if it's more than ~20% of tickets, the scale has stopped meaning anything.

Priority ≠ queue-jumping approval

A P1 New Feature still needs a BRD and a roadmap slot. Priority speeds up the path; it doesn't delete the gates. The only true bypass is P0, and only for bugs.

IT lead-time rules — carried over from the original

14 DAYS New campaign

Reserve at least 14 days for IT preparation. Clarified: the clock starts at approval (Step 3), not at proposal — and IT confirms the achievable date back to the requester at Step 1 so nobody plans against a date IT never agreed to.

3 DAYS Out-of-hours support

Special arrangement for IT support outside working hours must be raised at least 3 days before the event.

3 DAYS Video conversion

Video converting takes 3 working days. Belongs on the campaign brief as an assets-ready-by dependency, not discovered at Step 4.

Gaps in the original — fixed in this version

1 No ticket ID

Labels only work if every request has one. One intake form → one ticket, prefixed CM- / CR- / NF- / BF-. Otherwise the legend lives only on the diagram and never in Asana.

2 Unbounded decline loop

"Revisit the details" had no round limit and no terminal state. Now: max 2 amend rounds, then the ticket moves to Parked / Won't Do with a reason. Requests should die out loud, not quietly.

3 "cc Agnes" is not an owner

Every ticket names one accountable owner at triage who carries it end-to-end. cc is visibility; it is not accountability.

4 SLA clock had no start

14 days from approval, stated on the ticket. Ambiguity here is what turns a lead-time rule into an argument.

5 Step 6 had no exit

Weekly review with no kill/extend criteria reviews forever. Now: hit KPI → extend · miss 2 consecutive cycles → kill or re-scope.

6 No build step for features

The original went approval → UAT with nothing in between. Fine for a campaign IT only configures; impossible for a feature. The NF lane inserts BRD → feasibility → slot → dev → QA.

Open questions — need a decision before this goes live

Q1 Who owns triage?

One named ops manager must own classification, or types will drift within a month. Who, and who covers when they're out?

Q2 What's the CR escalation threshold?

"Over N dev-days or has budget impact → Alex." N = ? and is there a dollar figure? Without a number, everything escalates and CR collapses back into CM.

Q3 Where does the intake form live?

Asana form is the obvious answer since the ticket lands there anyway. Confirm — and confirm whether regional teams get separate forms or one shared form with a region field.

Q4 Does Alex approve NF alone?

The NF lane assumes Alex + Product jointly hold the roadmap slot. If it's Alex alone, the "Product" box comes off the diagram.

Q5 Regional autonomy

Can HK / TW / SEA each run CM lanes in parallel against the same IT capacity, or is there one shared queue with a cap? This determines whether the 14-day SLA is per-request or per-region.

Q6 Colour-coding in Asana

Cheapest win: mirror these four colours as Asana tags so the type is readable in the board, not just here.
