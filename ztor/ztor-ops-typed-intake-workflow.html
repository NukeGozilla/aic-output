Definitions

CM Campaign / Content

A time-boxed push that uses only what already exists — a promo, content drop, seasonal event, or pricing change. Nothing new is built; things are configured, scheduled and launched against a date. A campaign that needs a new capability to run is two tickets, not one — a CM for the campaign, an NF/CR for the capability, with the CM blocked on it. Same campaign across HK + TW + SEA is one CM ticket with regional subtasks, not three.

CR Change Request

A change to something that already exists on a live surface — a copy, a rule, a threshold, a config value, a layout tweak. The screen or capability is already there; only its behavior or content changes.

NF New Feature

A capability that doesn't exist yet — a new screen, a new data model, a new integration, or a new business rule. Needs a BRD before anything else happens, even if it "feels small."

BF Bug Fix

Something built is not behaving as specified. If it behaves as specified but the spec itself is wrong, that's a Change Request, not a bug — re-route it, never close as "working as intended."

Priority is a second axis — not a fifth type

Two axes, never merged

Type = what kind of work it is, and therefore which path it walks. Priority = how urgent it is, and therefore how fast that path runs. Every ticket carries both. "Urgent" is not a type, and a New Feature can be High without becoming a bug. Critical is reserved for incidents, not urgency.

Guardrail

Critical / High inflation

If everything is Critical or High, nothing is. Only Ops Mgr or IT lead can set High, and only an actual incident is Critical — requesters propose, triage decides. Review the count monthly; if it's more than ~20% of tickets, the scale has stopped meaning anything.

Priority ≠ queue-jumping approval

A High New Feature still needs a BRD and a roadmap slot. Priority speeds up the path; it doesn't delete the gates. The only true bypass is Critical, and only for bugs.

IT lead-time rules

14 DAYS New campaign

Reserve at least 14 days for IT preparation. The clock starts at approval (Step 3), not at proposal. IT confirms the achievable date back to the requester at Step 1, so nobody plans against a date IT never agreed to.

3 DAYS Out-of-hours support

Special arrangement for IT support outside working hours must be raised at least 3 days before the event.

3 DAYS Video conversion

Video converting takes 3 working days. Put it on the campaign brief as an assets-ready-by date — don't discover it at Step 4.

Working rules — apply to every ticket

1 One request = one ticket

Every request is one Asana task on the matching board. The task URL is the ID and the board is the type. CR and NF share a board, so the Type field on that board (Change Request / Feature) carries the split.

2 One accountable owner

Every ticket names one owner at triage who carries it end-to-end. cc is visibility; it is not accountability.
