1 · Purpose

Sell Bookyay-origin event tickets on ztor.com — solo tickets and ticket+merch bundles — with the entire customer experience (brand, checkout, wallet, support) on Ztor, while Bookyay remains the system of record for events and inventory. Consignment model: Bookyay wholesales, Ztor retails. Confirmed 2026-08-27 as the permanent operating model (no self-serve, ever).

3 · Scope

In:

  • Bookyay-origin GA (non-seated) events
  • Solo tickets + ticket+merch bundles on ztor.com (web)
  • Ztor gateway, fiat
  • My Wallet e-tickets
  • Venue scanning via existing Bookyay Organizer App
  • CS admin order ops: lookup / void only — refund requests handled offline (Ztor CS mailbox); system never moves money, ops refunds on the gateway console
  • Sales data sync back to Bookyay — one-way batch (ticket status · ticket inventory · transaction details, payload BR-63), every transaction tagged ztor_tag
  • CS admin reporting
  • Ops flows (defined in §6): event change · event cancel · allocation top-up · reduce · release-back

In — Bookyay side:

  • ztor_tag support in Bookyay's system — lets their ops/finance split Bookyay-channel vs Ztor-channel sales in reporting (BR-60/62)
  • Event + allocation API feed to Ztor: event data, quantity, continuous updates (BR-02/10)
  • Pre-issue QRs at allocation; take back returned QRs on reduce / release-back (BR-02/51/52)
  • Accept the batch sync-back: ticket status · inventory burn-down · transactions (BR-60/63)
  • Per-event organizer_login scoping for venue scanning (BR-31; feasibility open #6)

Out (explicit):

  • Seated events
  • Creator self-serve (killed 08-27, permanent)
  • Queue-It / spike infra (small curated events only)
  • App support at launch (web-first, ~10 events; app shows redirect)
  • POPCORN / crypto payment
  • Money settlement between companies (same group — ztor_tag only)
  • WhatsApp / IG support channels
  • Organizer partnerships
  • Bookyay storefront changes

5 · Requirements

A · Intake & allocation (Bookyay side)

  • BR-01 Bookyay admin selects which events sell on Ztor (curated; Excel intake from creators/ops).
  • BR-02 Per selected event, Bookyay sets one allocation (quantity, tier, price) and pre-issues that quantity of tickets; QR payloads transfer to Ztor with the allocation. MVP: allocation = full event inventory (take-all, 09-07) — top-up/reduce/release-back stay specced but become edge flows.
  • BR-03 Pre-issued QRs MUST be scannable by the unchanged Bookyay Organizer App (no rebrand).

B · Creator Studio (admin-operated)

  • BR-10 Auto-import (09-03, = designer D238): once a creator's Bookyay account is bound, ALL their allocated events import automatically and land as pending-setup (待設定套組). Sync (09-07): CS auto-pulls latest event data from Bookyay hourly; CS admin also has a manual sync button. Event fields display-only from the feed (incl. description); images re-uploaded to Ztor specs. No manual per-event import.
  • BR-11 creator_mapping required before publish (publish gate). Unmapped organizers: pending account + invitation (IP Bank pattern).
  • BR-12 Admin creates sale_items against the allocation: solo_ticket and/or bundle; each takes a reservation; sum of reservations ≤ allocation. Reservations may be re-balanced mid-sale (floor = sold count per sale_item).
  • BR-13 Bundle = ticket(s) + ≥1 eShop merch SKU, one combined price, fiat only. Every unit carries its own QR (09-03: 4-item order → 4 QRs): each ticket = a pre-issued Bookyay QR; each merch = an eShop pickup QR.
  • BR-14 T&C: Bookyay's terms inherited; Ztor-specific T&C version if legal requires (open #20).

C · Storefront & checkout (ztor.com, web)

  • BR-20 Event listing + event detail pages; buyers cannot distinguish event classes (future-proofing; Phase 1 = Bookyay-origin only).
  • BR-21 Checkout on Ztor gateway; no call to Bookyay in the payment path (checkout works when Bookyay is down).
  • BR-22 Per-buyer purchase cap per event: NEEDS-POLICY-OWNER (number).
  • BR-23 App: no native ticketing; orders screen deep-links/redirects to web.
  • BR-24 Loyalty: deferred out of 2.3 (09-03 — VIP/Loyalty/KYC cut from the release). No points display at ticket purchase Phase 1; retro-credit question moves to the loyalty stream.
  • BR-25 Pricing & currency: Bookyay sets the allocation price in the event's base currency (NEEDS-POLICY-OWNER for Phase 1); ztor.com displays per the Ztor currency model — user display currency by registration IP, Ztor-controlled FX table, no live FX.

D · Fulfilment

  • BR-30 On payment capture, one pre_issued_ticket per ticket sold is atomically assigned to the order; buyer sees QR in my_wallet + receives an email confirmation carrying the ticket.
  • BR-31 Venue entry: staff scans with Organizer App under a per-event organizer_login (cannot see or scan other events). Feasibility owner: Bookyay.
  • BR-32 Tickets are bearer QRs (no identity check at door); transfer-by-forwarding implicitly allowed. Accepted risk — §9.

E · Post-sale & support

  • BR-40 Refund requests handled offline via the Ztor CS mailbox (no buyer self-service, no in-system refund). System action = void only: admin voids the transaction → ticket voided → void syncs to Bookyay. Money refund executed by ops on the gateway console (Stripe/Antom) — the system never moves money. Bundles: whole-bundle only — ticket voided + merch leg refunded (pre-shipment) per eShop policy. Buyer-facing copy says 取消, never 退款 (09-03).
  • BR-41 Order statuses: paid, fulfilled, refunded, voided, cancelled — visible in CS order lookup.
  • BR-42 Event change (Bookyay BO edit) → arrives via the hourly auto-pull / manual sync (BR-10) → listing/CS auto-update → buyers notified (email minimum; in-app optional Phase 1), wallet refreshes.
  • BR-43 Event cancel (Bookyay BO) → push → pause + delist → all Ztor tickets voided, voids sync back; buyer refunds executed by ops on the gateway (BR-40 model). Bundle merch on cancel: NEEDS-POLICY-OWNER. (Ztor-originated cancel evaluated & rejected 09-04 — future co-sale keeps Bookyay the lifecycle owner. Closed; don't reopen.)
  • BR-44 Refund cutoff before doors: NEEDS-POLICY-OWNER (no refunds within N hours of event start, so voids propagate before scanning).

F · Inventory lifecycle

  • BR-50 Top-up: Bookyay allocates + pre-issues more; Ztor sellable pool grows live.
  • BR-51 Reduce (Bookyay-initiated): capped at unsold at the moment it lands (racing sale wins; sold tickets never claw back). Zero remaining → sold_out (listed, not delisted). Returned QRs re-enter Bookyay's pool.
  • BR-52 Release-back: unsold tickets auto-return at sale-window close (or manual).
  • BR-53 If assignment fails at capture (pool exhausted by a racing reduce), the payment auto-reverses (checkout-path reversal — distinct from BR-40 ops refunds); buyer sees sold-out. A paid order is never left ticketless.

G · Sync & reporting

  • BR-60 sync_back one-way, batch: auto daily + manual sync button in CS admin (09-07, same pattern as BR-10). Payload: sales, voids, burn-down, each with ztor_tag. Idempotent + replayable. Void propagation must beat the venue scan — technical solution owned by Eric (open #10); candidate: CS void action calls Bookyay's void API directly (synchronous, ops-plane — checkout path stays call-free); fallback: manual sync on event day + refund cutoff (BR-44).
  • BR-61 PII minimization: sync carries order refs + quantities + amounts, not buyer PII. Buyer data stays on Ztor; Bookyay ops views via CS lookup on escalations.
  • BR-63 sync_back payload (specced 09-07) — three record types per batch; envelope = batch id + generated_at (drives BR-60 idempotent replay):
RecordOne perFields
Ticket statuspre_issued_ticket that changedBookyay ticket_id · new state (assigned / voided / returned) · changed_at · Ztor order ref
Ticket inventory (burn-down)eventevent id · allocation qty · assigned · voided · returned · remaining sellable · as-of
Transaction detailsorderorder ref · event id · ztor_tag · sale_item type (solo / bundle) · ticket qty · amount + currency · status (paid / refunded / voided / cancelled) · paid_at / refunded_at

No buyer PII in any record (BR-61). Bundle amount attribution — report full bundle price or ticket-leg only: NEEDS-POLICY-OWNER (open #22).

  • BR-62 Ztor = system of record for Ztor sales. MVP day-to-day reporting home = Bookyay BO (fed by the daily sync, 09-07); CS keeps order lookup for support (eShop Transaction UI extension). Creator sales reports on ztor.com in December (milestone rev 09-02).

7 · State machines (total)

pre_issued_ticket: pre_issued → assigned (capture) · assigned → redeemed (scan) · assigned → voided (refund / cancel) · pre_issued → returned (release-back / reduce). Illegal: redeemed → * · returned → assigned (returned QRs re-enter only via a new allocation).

event-on-Ztor: imported → mapped → sale_setup → published ↔ paused → sold_out → closed · * → cancelled (Bookyay push). Illegal: publish without mapped.

allocation: active → exhausted (all assigned) · active → reduced (BR-51) · active/reduced → closed (window end, release-back done).

8 · Non-functional

  • Checkout latency/availability independent of Bookyay — zero synchronous cross-system calls in the purchase path.
  • Volumes: curated small events; ~10 events on web before app; no spike infra.
  • Sync monitoring + alert on batch failure; replays safe (idempotent).

9 · Assumptions, dependencies, accepted risks

  • A1 CS order-ops console (lookup/void) is Ztor-built — no refund function; money moves only on the gateway console
  • A2 (revised 08-27) separate Ztor CS team + email
  • A3 ✓ one-way batch sync
  • A4 ✓ pre-issued QR + unchanged Organizer App (scoped logins pending)
  • A5 ✓ no money settlement — ztor_tag only
  • Dependencies: Bookyay pre-issue at allocation (validated verbally 08-27) · organizer_login scoping feasibility (Bookyay, open) · TW gateway (Airwallex eval — payout side; does not block ticket sales on current rails) · eShop shipping work for bundle merch fulfilment (2.3 stream).
  • Accepted risks: static bearer QR (screenshot transfer possible — small curated events; confirm whether pre-issue supports Bookyay's dynamic QR, else accept) · Bookyay BO view trails Ztor by ≤ one sync window.

12 · Acceptance (condensed)

  • 1. Event with allocation 100 + pre-issued QRs appears in CS import; publish blocked until creator_mapping.
  • 2. Solo + bundle sale_items reserve from one allocation; reservations cannot exceed allocation.
  • 3. Buyer completes checkout with Bookyay API unreachable.
  • 4. On capture: ticket assigned atomically; QR in my_wallet + email; Organizer App scans it under the event's scoped login and rejects it for any other event.
  • 5. CS void → ticket voided + void in Bookyay within one sync window; voided QR rejected at scan. (Money refund runs on the gateway console, outside the system.)
  • 6. Event cancel → delist + all tickets voided; buyer refunds by ops per BR-40; bundle merch per resolved policy #2.
  • 7. Reduce mid-sale → capped at unsold; racing sale wins; zero remaining shows sold_out (listed).
  • 8. Release-back returns exactly (allocation − assigned).
  • 9. Every Ztor transaction visible in Bookyay reporting with ztor_tag within one sync window; no buyer PII in the payload.
  • 10. BR-53 path auto-refunds; a paid order is never ticketless.
  • 11. An imported event in CS shows no ticket-issuance, scanner, check-in, cancel, or delete surfaces; capacity is not editable (§6b).
