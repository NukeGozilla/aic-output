1 · Purpose

Sell Bookyay-origin event tickets on ztor.com — solo tickets and ticket+merch bundles — with the entire customer experience (brand, checkout, wallet, support) on Ztor, while Bookyay remains the system of record for events and inventory. Consignment model: Bookyay wholesales, Ztor retails. Confirmed 2026-08-27 as the permanent operating model (no self-serve, ever).

2 · Vocabulary (contract — reuse verbatim everywhere)

3 · Scope

In: Bookyay-origin GA (non-seated) events · solo tickets + bundles on ztor.com (web) · Ztor gateway, fiat · My Wallet e-tickets · venue scanning via existing Bookyay Organizer App · CS admin order-ops (lookup / refund / void) · one-way sync-back + store_tag · CS admin reporting · ops flows (change / cancel / top-up / reduce / release-back).

Out (explicit): seated events · creator self-serve (killed 08-27, permanent) · Queue-It / spike infra (small curated events only) · app support at launch (web-first, ~10 events; app shows redirect) · POPCORN / crypto payment · money settlement between companies (same group — store_tag only) · WhatsApp/IG support channels · organizer partnerships · Bookyay storefront changes.

5 · Requirements

A · Intake & allocation (Bookyay side)

  • BR-01 Bookyay admin selects which events sell on Ztor (curated; Excel intake from creators/ops).
  • BR-02 Per selected event, Bookyay sets one allocation (quantity, tier, price) and pre-issues that quantity of tickets; QR payloads transfer to Ztor with the allocation.
  • BR-03 Pre-issued QRs MUST be scannable by the unchanged Bookyay Organizer App (no rebrand).

B · Creator Studio (admin-operated)

  • BR-10 Allocated events appear in a CS import list (event fields display-only, inherited from Bookyay incl. description; images re-uploaded to Ztor specs).
  • BR-11 creator_mapping required before publish (publish gate). Unmapped organizers: pending account + invitation (IP Bank pattern).
  • BR-12 Admin creates sale_items against the allocation: solo_ticket and/or bundle; each takes a reservation; sum of reservations ≤ allocation. Reservations may be re-balanced mid-sale (floor = sold count per sale_item).
  • BR-13 Bundle = one ticket + ≥1 eShop merch SKU, one combined price, fiat only.
  • BR-14 T&C: Bookyay's terms inherited; Ztor-specific T&C version if legal requires (open #6).

C · Storefront & checkout (ztor.com, web)

  • BR-20 Event listing + event detail pages; buyers cannot distinguish event classes (future-proofing; Phase 1 = Bookyay-origin only).
  • BR-21 Checkout on Ztor gateway; no call to Bookyay in the payment path (checkout works when Bookyay is down).
  • BR-22 Per-buyer purchase cap per event: NEEDS-POLICY-OWNER (number).
  • BR-23 App: no native ticketing; orders screen deep-links/redirects to web.
  • BR-24 Ticket + bundle purchases accrue loyalty points per the platform loyalty model (any transaction earns points). If VIP loyalty ships after ticketing, accrual retro-vs-waive: NEEDS-POLICY-OWNER.
  • BR-25 Pricing & currency: Bookyay sets the allocation price in the event's base currency (NEEDS-POLICY-OWNER for Phase 1); ztor.com displays per the Ztor currency model — user display currency by registration IP, Ztor-controlled FX table, no live FX.

D · Fulfilment

  • BR-30 On payment capture, one pre_issued_ticket per ticket sold is atomically assigned to the order; buyer sees QR in my_wallet + receives an email confirmation carrying the ticket.
  • BR-31 Venue entry: staff scans with Organizer App under a per-event organizer_login (cannot see or scan other events). Feasibility owner: Bookyay.
  • BR-32 Tickets are bearer QRs (no identity check at door); transfer-by-forwarding implicitly allowed. Accepted risk — §9.

E · Post-sale & support

  • BR-40 Refunds CS-only (no buyer self-service). Store CS mailbox (own team + email). Refund executes on Ztor gateway via a CS refund console; ticket → voided; void syncs to Bookyay. Bundle refunds are whole-bundle only: ticket voided + merch leg refunded (pre-shipment) per eShop policy.
  • BR-41 Order statuses: paid, fulfilled, refunded, voided, cancelled — visible in CS order lookup.
  • BR-42 Event change (Bookyay BO edit) → push to Ztor → listing/CS auto-update → buyers notified (email minimum; in-app optional Phase 1), wallet refreshes.
  • BR-43 Event cancel (Bookyay BO) → push → pause + delist → auto-refund all Ztor orders on Ztor gateway → voids sync back. Bundle merch on cancel: NEEDS-POLICY-OWNER.
  • BR-44 Refund cutoff before doors: NEEDS-POLICY-OWNER (no refunds within N hours of event start, so voids propagate before scanning).

F · Inventory lifecycle

  • BR-50 Top-up: Bookyay allocates + pre-issues more; Ztor sellable pool grows live.
  • BR-51 Reduce (Bookyay-initiated): capped at unsold at the moment it lands (racing sale wins; sold tickets never claw back). Zero remaining → sold_out (listed, not delisted). Returned QRs re-enter Bookyay's pool.
  • BR-52 Release-back: unsold tickets auto-return at sale-window close (or manual).
  • BR-53 If assignment fails at capture (pool exhausted by a racing reduce), the order auto-refunds; buyer sees sold-out. A paid order is never left ticketless.

G · Sync & reporting

  • BR-60 sync_back one-way, batch: sales, voids, burn-down, each with store_tag. Idempotent + replayable; latency target NEEDS-POLICY-OWNER (proposed ≤ 15 min).
  • BR-61 PII minimization: sync carries order refs + quantities + amounts, not buyer PII. Buyer data stays on Ztor; Bookyay ops views via CS lookup on escalations.
  • BR-62 Ztor = system of record for Ztor sales. CS admin reporting ships Phase 1 (eShop Transaction UI extension); creator sales reports on ztor.com in November; Bookyay BO keeps the combined cross-channel view via sync.

6 · Ops flows (normative)

Change / cancel / top-up / reduce / release-back — as drawn in one-pager tab C (C3) + material S10; part of this BRD by reference.

7 · State machines (total)

pre_issued_ticket: pre_issued → assigned (capture) · assigned → redeemed (scan) · assigned → voided (refund / cancel) · pre_issued → returned (release-back / reduce). Illegal: redeemed → * · returned → assigned (returned QRs re-enter only via a new allocation).

event-on-Ztor: imported → mapped → sale_setup → published ↔ paused → sold_out → closed · * → cancelled (Bookyay push). Illegal: publish without mapped.

allocation: active → exhausted (all assigned) · active → reduced (BR-51) · active/reduced → closed (window end, release-back done).

8 · Non-functional

  • Checkout latency/availability independent of Bookyay — zero synchronous cross-system calls in the purchase path.
  • Volumes: curated small events; ~10 events on web before app; no spike infra.
  • Sync monitoring + alert on batch failure; replays safe (idempotent).

9 · Assumptions, dependencies, accepted risks

  • A1 CS order-ops console (lookup/refund/void) is Ztor-built. A2 (revised 08-27) separate Store CS team + email. A3 ✓ one-way batch sync. A4 ✓ pre-issued QR + unchanged Organizer App (+ scoped logins pending). A5 ✓ no money settlement — store_tag only.
  • Dependencies: Bookyay pre-issue at allocation (validated verbally 08-27) · organizer_login scoping feasibility (Bookyay, open) · TW gateway (Airwallex eval — payout side; does not block ticket sales on current rails) · eShop shipping work for bundle merch fulfilment (2.3 stream).
  • Accepted risks: static bearer QR (screenshot transfer possible — small curated events; confirm whether pre-issue supports Bookyay's dynamic QR, else accept) · Bookyay BO view trails Ztor by ≤ one sync window.

12 · Acceptance (condensed)

  • Event with allocation 100 + pre-issued QRs appears in CS import; publish blocked until creator_mapping.
  • Solo + bundle sale_items reserve from one allocation; reservations cannot exceed allocation.
  • Buyer completes checkout with Bookyay API unreachable.
  • On capture: ticket assigned atomically; QR in my_wallet + email; Organizer App scans it under the event's scoped login and rejects it for any other event.
  • CS refund → gateway refund + voided + void in Bookyay within one sync window; voided QR rejected at scan.
  • Event cancel → delist + auto-refund all orders; bundle merch per resolved policy #2.
  • Reduce mid-sale → capped at unsold; racing sale wins; zero remaining shows sold_out (listed).
  • Release-back returns exactly (allocation − assigned).
  • Every Ztor transaction visible in Bookyay reporting with store_tag within one sync window; no buyer PII in the payload.
  • BR-53 path auto-refunds; a paid order is never ticketless.
