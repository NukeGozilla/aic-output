1 · Purpose

Sell Bookyay-origin event tickets on ztor.com — solo tickets and ticket+merch bundles — with the entire customer experience (brand, checkout, wallet, support) on Ztor, while Bookyay remains the system of record for events and inventory. Consignment model: Bookyay wholesales, Ztor retails. Confirmed 2026-08-27 as the permanent operating model (no self-serve, ever).

2 · Vocabulary (contract — reuse verbatim everywhere)

sale_itemWhat Ztor sells against an allocation: solo_ticket or bundle (ticket + eShop merch, one payment)
reservationA sub-quantity of an allocation earmarked to one sale_item (e.g. 50 of 100 to a bundle)

sync_backOne-way, batch, non-transactional feed Ztor → Bookyay: ticket status · ticket inventory · transaction details (payload BR-63). Nothing in checkout waits on it
organizer_loginPer-event-scoped account for the Bookyay Organizer App (venue scanning)

3 · Scope

In:

  • Bookyay-origin GA (non-seated) events
  • Solo tickets + ticket+merch bundles on ztor.com (web)
  • Ztor gateway, fiat
  • My Wallet e-tickets
  • Venue scanning via existing Bookyay Organizer App
  • CS admin order ops: lookup / void only — refund requests handled offline (Ztor CS mailbox); system never moves money, ops refunds on the gateway console
  • Sales data sync back to Bookyay — one-way batch (ticket status · ticket inventory · transaction details, payload BR-63), every transaction tagged ztor_tag
  • CS admin reporting
  • Ops flows (defined in §6): event change · event cancel · allocation top-up · reduce · release-back

In — Bookyay side:

  • ztor_tag support in Bookyay's system — lets their ops/finance split Bookyay-channel vs Ztor-channel sales in reporting (BR-60/62)
  • Event + allocation API feed to Ztor: event data, quantity, lifecycle + scan status, continuous updates (BR-04)
  • Pre-issue QRs at allocation; take back returned QRs on reduce / release-back (BR-02/51/52)
  • Accept the batch sync-back: ticket status · inventory burn-down · transactions (BR-60/63)
  • Per-event organizer_login scoping for venue scanning (BR-31; feasibility open #5)

Out (explicit):

  • Seated events
  • Creator self-serve (killed 08-27, permanent)
  • Queue-It / spike infra (small curated events only)
  • App sales at launch (web-first, ~10 events; app = web handoff + read-only order visibility, BR-23)
  • POPCORN / crypto payment
  • Money settlement between companies (same group — ztor_tag only)
  • WhatsApp / IG support channels
  • Organizer partnerships
  • Bookyay storefront changes

5 · Requirements

A · Intake & allocation (Bookyay side)

  • BR-01 Bookyay admin selects which events sell on Ztor (curated; Excel intake from creators/ops). 〔WF §7〕
  • BR-02 Per selected event, Bookyay sets one allocation (quantity, tier, price) and pre-issues that quantity of tickets; QR payloads transfer to Ztor with the allocation. MVP: allocation = full event inventory (take-all, 09-07) — top-up/reduce/release-back stay specced but become edge flows. 〔WF §7〕
  • BR-03 Pre-issued QRs MUST be scannable by the unchanged Bookyay Organizer App (no rebrand). 〔WF §7〕
  • BR-04 Event feed (Bookyay → Ztor): Bookyay exposes an API feed of every allocated event — event data, allocation quantity, lifecycle status (change / cancel), and per-ticket scan status (BR-64). Ztor auto-pulls hourly + manual sync button (BR-10); event changes and cancels arrive through this feed (§6). 〔WF §7〕

B · Creator Studio (admin-operated)

  • BR-10 Auto-import (09-03; scope corrected 09-07): Bookyay has no creator profile — the feed is a flat list of all events allocated to Ztor, not per-creator. Every allocated event imports automatically. Its status is derived on the Ztor side from setup progress — not a feed field: 待對應創作者 (BR-11) → 待設定販售項目 (sale items, BR-12) → publishable (= §7 imported → mapped → sale_setup → published). Sync (09-07): CS auto-pulls the BR-04 feed hourly; CS admin also has a manual sync button. Event fields inherit from the feed; presentation fields — display name · description · lineup display — may be optionally overridden in CS for Ztor UI needs (09-07): an overridden field stops tracking the feed (one-click revert to feed value). Locked (never overridable): date/time · venue · event type · capacity. Images re-uploaded to Ztor specs. No manual per-event import. 〔WF §4〕
  • BR-11 creator_mapping = a per-event step in CS after import (Bookyay has no creator concept); required before publish (publish gate). Unmapped organizers: pending account + invitation (IP Bank pattern). 〔WF §4〕
  • BR-12 Admin creates sale_items against the allocation: solo_ticket and/or bundle; each takes a reservation; sum of reservations ≤ allocation. Reservations may be re-balanced mid-sale (floor = sold count per sale_item). 〔WF §4〕
  • BR-13 Bundle = ticket(s) + ≥1 eShop merch SKU, one combined price, fiat only. Every unit carries its own QR (09-03: 4-item order → 4 QRs): each ticket = a pre-issued Bookyay QR; each merch = an eShop pickup QR. 〔WF §4〕
  • BR-14 T&C: Bookyay's terms inherited; Ztor-specific T&C version if legal requires (open #18).

C · Storefront & checkout (ztor.com, web)

  • BR-20 Event listing + event detail pages; buyers cannot distinguish event classes (future-proofing; Phase 1 = Bookyay-origin only). 〔WF §1〕
  • BR-21 Checkout on Ztor gateway; no call to Bookyay in the payment path (checkout works when Bookyay is down). 〔WF §2〕
  • BR-22 Per-buyer purchase cap per event: number TBD — biz decides Wed (open #1). 〔WF §2〕
  • BR-23 App (Phase 1 — no in-app sales): event & ticket purchases are web-only. What the app user sees: (a) event/eShop entry points hand off to mobile web (「前往 ztor.com」, opens in-app browser) — no dead-end storefront; (b) ticket orders bought on web appear read-only in the app order list, deep-linking to the web My Wallet for the QR; (c) no purchase flow, no native wallet render — app sales come after web proves smooth (§11). Exact surfaces & copy = design work (open #22; 09-03 direction split — full visibility vs minimal app — to align). 〔WF §8〕
  • BR-24 Loyalty: deferred out of 2.3 (09-03 — VIP/Loyalty/KYC cut from the release). No points display at ticket purchase Phase 1; retro-credit question moves to the loyalty stream.
  • BR-25 Pricing & currency: Bookyay sets the allocation price in the event's base currency (TBD — biz decides Wed, open #3); ztor.com displays per the Ztor currency model — user display currency by registration IP, Ztor-controlled FX table, no live FX. 〔WF §1〕

D · Fulfilment

  • BR-30 On payment capture, one pre_issued_ticket per ticket sold is atomically assigned to the order; buyer sees QR in my_wallet + receives an email confirmation carrying the ticket. 〔WF §3〕
  • BR-31 Venue entry: staff scans with Organizer App under a per-event organizer_login (cannot see or scan other events). Feasibility owner: Bookyay. 〔WF §7〕
  • BR-32 Tickets are bearer QRs (no identity check at door); transfer-by-forwarding implicitly allowed. Accepted risk — §9. 〔WF §3〕

E · Post-sale & support

  • BR-40 No buyer-facing refund offering. Requests handled offline via the Ztor CS mailbox; outcome communicated back to the buyer by email. System action = void only: admin voids the transaction → ticket voided → void syncs to Bookyay. Money refund executed by ops on the gateway console (Stripe/Antom) — the system never moves money. Bundles: whole-bundle only — ticket voided + merch leg refunded (pre-shipment) per eShop policy. Buyer-facing copy says 取消, never 退款 (09-03). 〔WF §6〕
  • BR-41 Order statuses: paid, fulfilled, refunded, voided, cancelled — visible in CS order lookup. 〔WF §6〕
  • BR-42 Event change (Bookyay BO edit) → arrives via the hourly auto-pull / manual sync (BR-10) → listing/CS auto-update → buyers notified (email minimum; in-app optional Phase 1), wallet refreshes. 〔WF §5〕
  • BR-43 Event cancel (Bookyay BO) → push → pause + delist → all Ztor tickets voided, voids sync back; buyer refunds executed by ops on the gateway (BR-40 model). Bundle merch on cancel: TBD — biz decides Wed (open #2). (Ztor-originated cancel evaluated & rejected 09-04 — future co-sale keeps Bookyay the lifecycle owner. Closed; don't reopen.) 〔WF §5〕

F · Inventory lifecycle

  • BR-50 Top-up: Bookyay allocates + pre-issues more; Ztor sellable pool grows live. 〔WF §5〕
  • BR-51 Reduce (Bookyay-initiated): capped at unsold at the moment it lands (racing sale wins; sold tickets never claw back). Zero remaining → sold_out (listed, not delisted). Returned QRs re-enter Bookyay's pool. 〔WF §5〕
  • BR-52 Release-back: unsold tickets auto-return at sale-window close (or manual). 〔WF §7〕
  • BR-53 If assignment fails at capture (pool exhausted by a racing reduce), the payment auto-reverses (checkout-path reversal — distinct from BR-40 ops refunds); buyer sees sold-out. A paid order is never left ticketless. 〔WF §2〕

G · Sync & reporting

  • BR-60 sync_back one-way, batch: auto daily + manual sync button in CS admin (09-07, same pattern as BR-10). Payload = the three BR-63 record types — ticket status · ticket inventory (burn-down) · transaction details — each with ztor_tag. Idempotent + replayable. Void propagation must beat the venue scan — technical solution owned by Eric (open #8); candidate: CS void action calls Bookyay's void API directly (synchronous, ops-plane — checkout path stays call-free); fallback: manual sync on event day. 〔WF §6〕
  • BR-61 No buyer personal data crosses to Bookyay: the sync-back carries order refs, quantities and amounts only — never the buyer's name, email, or phone number. Buyer data lives only on Ztor; when Bookyay ops needs details on an escalation, they look it up in CS instead of receiving it in the feed.
  • BR-62 Ztor = system of record for Ztor sales. MVP day-to-day reporting home = Bookyay BO (fed by the daily sync, 09-07); CS keeps order lookup for support (eShop Transaction UI extension). Creator sales reports on ztor.com in December (milestone rev 09-02). 〔WF §7〕
  • BR-63 sync_back payload (specced 09-07) — three record types per batch; envelope = batch id + generated_at (drives BR-60 idempotent replay): 〔WF §6〕
RecordOne perFields
Ticket statuspre_issued_ticket that changedBookyay ticket_id · new state (assigned / voided / returned) · changed_at · Ztor order ref
Ticket inventory (burn-down)eventevent id · allocation qty · assigned · voided · returned · remaining sellable · as-of
Transaction detailsorderorder ref · event id · ztor_tag · sale_item type (solo / bundle) · ticket qty · amount + currency · status (paid / refunded / voided / cancelled) · paid_at / refunded_at

No buyer personal data in any record (BR-61). Bundle amount attribution — report full bundle price or ticket-leg only: TBD (open #20, Jeff + Bookyay finance).

  • BR-64 Scan-status feed (Bookyay → Ztor, read-only; ruled 09-07 — closes C1): per imported event, per-ticket check-in status (redeemed / pending). CS event detail shows 已入場 / 未入場 lists, read-only — no scan actions in CS (scanning stays in the Organizer App, BR-31). Refresh rides the hourly pull + manual sync (BR-10); event-day freshness = manual sync. 〔WF §5〕

6b · Imported-event mode — CS contract (new 09-06; the bridge to the designer's native spec suite)

Bookyay is the ticket engine. The designer's 5.1.6.x suite is the native target state; an imported (consigned) event behaves differently on exactly these points — everything else follows the native spec. Visual demo: feature wireframes (§5 shows this contract on screen).

7 · State machines (total)

pre_issued_ticket: pre_issued → assigned (capture) · assigned → redeemed (scan) · assigned → voided (refund / cancel) · pre_issued → returned (release-back / reduce). Illegal: redeemed → * · returned → assigned (returned QRs re-enter only via a new allocation).

event-on-Ztor: imported → mapped → sale_setup → published ↔ paused → sold_out → closed · * → cancelled (Bookyay push). Illegal: publish without mapped. UI labels: imported = 待對應創作者 · mapped/sale_setup = 待設定販售項目 · published = 已發布.

allocation: active → exhausted (all assigned) · active → reduced (BR-51) · active/reduced → closed (window end, release-back done).

8 · Non-functional

  • Checkout latency/availability independent of Bookyay — zero synchronous cross-system calls in the purchase path.
  • Volumes: curated small events; ~10 events on web before app; no spike infra.
  • Sync monitoring + alert on batch failure; replays safe (idempotent).

  • A4 ✓ pre-issued QR + unchanged Organizer App (scoped logins pending)

  • Dependencies: Bookyay pre-issue at allocation (validated verbally 08-27) · organizer_login scoping feasibility (Bookyay, open) · TW gateway (Airwallex eval — payout side; does not block ticket sales on current rails) · eShop shipping work for bundle merch fulfilment (2.3 stream).
  • Accepted risks: static bearer QR (screenshot transfer possible — small curated events; confirm whether pre-issue supports Bookyay's dynamic QR, else accept) · Bookyay BO view trails Ztor by ≤ one sync window.

12 · Acceptance (condensed)

  • 1. Event with allocation 100 + pre-issued QRs appears in CS import; publish blocked until creator_mapping.
  • 2. Solo + bundle sale_items reserve from one allocation; reservations cannot exceed allocation.
  • 3. Buyer completes checkout with Bookyay API unreachable.
  • 4. On capture: ticket assigned atomically; QR in my_wallet + email; Organizer App scans it under the event's scoped login and rejects it for any other event.
  • 5. CS void → ticket voided + void in Bookyay within one sync window; voided QR rejected at scan. (Money refund runs on the gateway console, outside the system.)
  • 6. Event cancel → delist + all tickets voided; buyer refunds by ops per BR-40; bundle merch per resolved policy #2.
  • 7. Reduce mid-sale → capped at unsold; racing sale wins; zero remaining shows sold_out (listed).
  • 8. Release-back returns exactly (allocation − assigned).
  • 9. Every Ztor transaction visible in Bookyay reporting with ztor_tag within one sync window; no buyer personal data in the payload.
  • 10. BR-53 path auto-refunds; a paid order is never ticketless.
  • 11. An imported event in CS shows no ticket-issuance, scanner, check-in, cancel, or delete surfaces; capacity is not editable (§6b).
