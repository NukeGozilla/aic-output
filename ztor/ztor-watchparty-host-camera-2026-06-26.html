✅ Decision update (2026-06-28 dev sync): LiveKit. Real-time tech for the host camera is LiveKit (WebRTC) — dev already stood up a working demo at stagingdev.ztor.ai/live-demo. Amazon IVS was evaluated but shelved for launch (correct long-term, but ~1+ week just for AWS env setup — too slow for the Aug 4 window); short-term Twitch also dropped. This page was the original IVS buy-in brief; it's updated below to reflect the LiveKit decision (the "Ably ≠ video / two-rails" framing still holds — only the media vendor changed).
1 · The ask
  • Let the host stream their own camera alongside the movie — a watch-along face-cam.
  • Fans see the host react in a small picture-in-picture (PiP) tile.
  • Purely additive: sync, chat, presence, tickets, and the back office are untouched.
2 · The reframe
Ably never carried video — the movie goes CDN → browser; Ably is a thin bus for play/pause/seek, chat, and presence. So the camera is not "a layer on Ably" — it's live media transport, which is its own service. Keep Ably. Add LiveKit for the camera. Replace nothing.
3 · Envelope — why the cheap path works
ConstraintValue

Scale≤ 1,000 viewers / room
LatencySub-second with LiveKit (a few seconds was acceptable, but real-time is better for live reactions)

Host-only + ≤1,000 + HK. LiveKit is a WebRTC SFU (one publisher → many subscribers) — real-time, and dev already has it working. (IVS-era note: a managed-HLS/no-SFU path was the original sketch when 3–5 s was the target; superseded.)

  • The host's browser publishes the webcam to LiveKit via its JS SDK — no OBS, no separate encoder.
  • LiveKit (a WebRTC SFU) fans the one host track out to up to 1,000 subscribers in real time.
  • The fan page runs two players: the movie (main, hls.js, off Ztor's CDN) + the host cam (PiP, a LiveKit subscriber).
  • Ably signals only the camera on/off so the PiP appears/disappears. It never touches video.
  • Movie and camera stay on separate rails — the movie never goes through LiveKit.
5 · Why LiveKit (decided 6-28)
  • Dev already has a working demo — stagingdev.ztor.ai/live-demo. Fastest path to the Aug 4 window for this team; no new AWS env to stand up.
  • Real-time (WebRTC) — sub-second, so the host's reactions feel live (vs the ~3–5 s of a managed-HLS approach).
  • The host publishes from the browser via LiveKit's JS SDK (no OBS install).
  • Open-source / flexible — LiveKit Cloud or self-host; not locked to one cloud vendor.
  • Amazon IVS was judged correct long-term but ~1+ week just for env setup — shelved for launch. Short-term Twitch also dropped.
6 · What changes in the build (small)

BackendMint a LiveKit room + access token per party (publish = host only, subscribe = ticket holders); close the room on host_away / ended.
UnchangedSync engine, chat, presence, tickets, BO grants.
7 · Out of scope (v1)
  • Viewer cameras (fans on cam) — would need fan-in / an SFU.
  • Sub-second host interactivity — the trigger to revisit a WebRTC SFU.
  • Recording / replay of the camera — live-only, matching the movie's no-replay rule.
8 · Cost
LiveKit Cloud bills on participant-minutes / bandwidth (host-only publish keeps the publish side cheap; the cost is fan-out to subscribers). Self-hosting the open-source SFU trades the bill for ops. Either way, scope it to 1 host track × ≤1,000 subscribers × session length and set a usage alarm.
9 · Resolved
Vendor — LiveKit (decided 2026-06-28). Browser publish via the LiveKit JS SDK (no OBS); dev has a working demo.

Assumed unless flagged: the camera carries the host's mic; LiveKit Cloud for launch (self-host is a later option). Open items for build: LiveKit room/token wiring + the per-party lifecycle (open on go-live, close on host-away/ended).
10 · LiveKit does not replace Ably
LiveKit carries the camera's pixels; Ably carries the room's state. Both are needed.
JobOwner
Host-authoritative sync (play / pause / seek)Ably — the movie isn't on LiveKit, so there's nothing there to sync to
Presence (who's watching)Ably
Live chatAbly (LiveKit has data channels, but no reason to rebuild chat we already have)
Camera on/off signalAbly
Host camera videoLiveKit
Keep them decoupled — they scale and fail independently (LiveKit down → sync + chat survive; Ably down → video keeps flowing).
TL;DR. Keep Ably for sync / chat / presence / signal. Add the host camera as a host-only stream on LiveKit (WebRTC SFU) — the host publishes from the browser via the LiveKit SDK (no OBS); dev already has a working demo. Two players on the fan page (movie via our CDN + PiP cam via a LiveKit subscriber); Ably just signals on/off. LiveKit ≠ Ably — pixels vs state, decoupled on purpose.
