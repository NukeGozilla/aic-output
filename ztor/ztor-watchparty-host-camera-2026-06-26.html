Watch Party — Host Camera Architecture Dev brief · Amazon IVS · 2026-06-26

How we let the host stream their own camera alongside the movie — a watch-along face-cam fans see as a picture-in-picture tile. Builds on the shipped Watch Party (Ably sync + host-authoritative playback + chat + presence). Decision: the camera rides Amazon IVS; Ably is unchanged.

▶ Live demo ↗ BRD Solution diagram Back office
1 · The ask
  • Let the host stream their own camera alongside the movie — a watch-along face-cam.
  • Fans see the host react in a small picture-in-picture (PiP) tile.
  • Purely additive: sync, chat, presence, tickets, and the back office are untouched.
2 · The reframe
Ably never carried video — the movie goes CDN → browser; Ably is a thin bus for play/pause/seek, chat, and presence. So the camera is not "a layer on Ably" — it's live media transport, which is its own service. Keep Ably. Add IVS for the camera. Replace nothing.

  • The host's browser publishes the webcam to Amazon IVS via the IVS Web Broadcast SDK — no OBS, no separate encoder.
  • IVS handles ingest + transcode + low-latency delivery (built-in CDN) and gives a playback URL.
  • The fan page runs two players: the movie (main, hls.js, off Ztor's CDN) + the host cam (PiP, the IVS URL).
  • Ably signals only the camera on/off so the PiP appears/disappears. It never touches video.
  • Movie and camera stay on separate rails — the movie never goes through IVS.
5 · Why IVS
  • Managed live video in one service; the host publishes from the browser (no OBS install).
  • Pay while streaming — no per-channel idle-cost trap (the reason we passed on the MediaLive + MediaPackage + CloudFront build).
  • Fastest to ship, lowest ops for a host-only broadcast.
  • A WebRTC SFU (Agora / LiveKit) would be overkill — reserve it only for sub-second host↔chat interactivity (or Agora, if China ever becomes required).

7 · Out of scope (v1)
  • Viewer cameras (fans on cam) — would need fan-in / an SFU.
  • Sub-second host interactivity — the trigger to revisit a WebRTC SFU.
  • Recording / replay of the camera — live-only, matching the movie's no-replay rule.
8 · Cost
IVS bills per host stream-hour + per viewer-hour delivered — no idle-channel cost. Set a billing alarm; otherwise predictable: roughly (host hours) + (attendee watch-hours).
9 · Open decision
Host publishing — confirm the IVS Web Broadcast SDK (browser). Recommended for v1: zero install, instant go-live, ideal for a casual reaction cam.

What we give up vs OBS/RTMP (pro-production only): ~720p ceiling (vs 1080p+), no scene composition / overlays / multi-source, no hardware encoders, slightly weaker bad-network resilience. None of it needed for a face-cam — and IVS also accepts RTMP, so OBS can be added later as a power-host fallback without re-architecting.

Assumed unless flagged: the camera carries the host's mic; IVS Low-Latency tier (right for 1,000 viewers, not the sub-300 ms Real-Time tier).
10 · IVS does not replace Ably
IVS carries the camera's pixels; Ably carries the room's state. Both are needed.
JobOwner
Host-authoritative sync (play / pause / seek)Ably — IVS has no such primitive, and the movie isn't on IVS
Presence (who's watching)Ably
Live chatAbly (IVS Chat exists, but no reason to split a 2nd vendor in)
Camera on/off signalAbly
Host camera videoIVS
Keep them decoupled — they scale and fail independently (IVS down → sync + chat survive; Ably down → video keeps flowing).
TL;DR. Keep Ably for sync / chat / presence / signal. Add the host camera as a host-only stream on Amazon IVS — the host publishes from the browser via the IVS SDK (no OBS, no WebRTC server). Two players on the fan page (movie via our CDN + PiP cam via IVS); Ably just signals on/off. Pay-while-streaming, predictable cost. IVS ≠ Ably — pixels vs state, decoupled on purpose.
