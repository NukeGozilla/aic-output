1. Scope

The rule: the Creator API is front-end only

Every endpoint in the Creator API is called by an artist site's front end (e.g. lloud.club). Anything else lives elsewhere:

  • Admin and configuration belong to Creator Studio.
  • Backend-to-backend calls are outside this API.

Sort every endpoint into three categories

The reference has 82 endpoints in 23 groups, and none of them says when it will be built. Two things make that a problem:

  • Eric's team builds the feature first, then exposes its API.
  • The site team will generate mock APIs from openapi.yaml, so whatever is in the file becomes build scope and launch expectation.

2. Catalog + Commerce

The principle: the Creator API owns its contract, Ztor owns the model

The Creator API is a separate API for standalone creator sites. It doesn't need to copy the dev team's internal Shopping API, so keep its shapes simple:

  • The creator is fixed by the site (from the channel key). Drop /creators/{c}/ paths and ?creator= parameters.
  • One shop per site. No seller objects, no carts grouped by shop, no multi-shop payment groups.

What the shapes can't do is promise behaviour the systems behind them don't have. Each shape has to carry these facts, checked against the dev team's eShop API (ztor20/creator-api → ztor-shopping-api.md):

Products have options (e.g. colour, size) and SKUs. Price and stock are per SKU sizes[], one price, per-size /inventory Model options + SKUs (SKU ID, price, stock). Stock comes with the product, so drop /inventory. Adding to the cart takes a SKU ID
Checkout = price quote the buyer confirms → submit → payment page (redirect) → result POST /orders returns paid immediately Submit returns a payment URL and a pending status. Add a quote step and a "check payment result" endpoint. Never return paid synchronously
Checkout takes a pickup contact (name + phone). There's no shipping-address field address_id (shipping) Use a pickup contact. Delivery: see section 3

  • size guide (LLOUD sells clothing)

Collections

  • For launch, the site keeps its own collection → product list in its content, next to each collection's choreography. Every new drop needs site work anyway, so this adds nothing extra.
  • The Creator API provides the site's product list and product detail, and the site groups them.
  • Collections as a Creator Studio feature, so a creator can launch a drop without site work, move to category 3.

Conventions

  • Remove X-Gateway-App-Token from the site's headers.
    • It's a server-only credential: the dev team's doc says it must never be placed in a browser.
    • Sites send X-Channel-Key plus the fan's Bearer token, and the Creator API adds the gateway token when it calls Ztor's systems.
    • This resolves the TO-CONFIRM.
  • Use one set of conventions everywhere: one error shape, one field casing, one pagination style, one timestamp format. Today the Conventions (the eShop envelope) and the endpoint samples disagree. Which set is the BA's choice; it just has to be consistent.
  • Add a "Backed by" column to each endpoint: which Ztor system and call serves it. Draft it from the dev team's eShop API (ztor20/creator-api), and Eric's team confirms.
  • Language is required on every call. The site sends its current language in Accept-Language (e.g. en-us on lloud.club), and passes it to the Ztor sign-in page (ui_locales) so a new account's language is set from it. Supported: en-us, zh-hk, zh-tw. The Channel's default_language (section 5) is only the safety net.

Shared with ztor.com by default, "No crossover" as an option

  • By default a site member is a Ztor user:
    • one account works on both the site and ztor.com
    • cart and order history show on both
    • the creator's products can sell on both
  • "No crossover" is a Creator Studio setting per site. When it's on:
    • accounts don't cross over: a ztor.com account can't sign in on the site, and a site account can't sign in on ztor.com
    • the same email can hold a site account and a separate Ztor account
    • cart and orders stay with the site account
    • all of the creator's products sell only on the site, not on ztor.com (exclusivity is per site, not per product)
  • It's chosen once, at setup, and locked once the site has members. Switching it later would mean splitting or merging accounts.
  • LLOUD launches with No crossover on.
  • What stays shared even when it's on: the Ztor sign-in page, Ztor's payment gateway, Creator Studio, Ztor's customer service team, and Ztor's email service. Whether emails carry the creator's branding is a management question (Open items).
  • Update the brief to match:
    • Design rule 04 (one identity) stays as it is: every site member has an account in Ztor's identity. Add one line: the No crossover setting decides whether that account can also be used on ztor.com.
    • AC-2.2 ("recognised on ztor.com — no second account") applies only when No crossover is off. With it on, the check becomes: a site account can't sign in on ztor.com, and a Ztor account can't sign in on the site.
    • Add the No crossover setting to the Channel data model.

3. Checkout — delivery, payment, order states

Delivery: pickup / pop-up only at launch

  • LLOUD launches with pickup / pop-up only. Delivery to an address is a later eShop feature.
  • Checkout takes a pickup contact (name + phone). There's no delivery address.
  • Each item gets its own pickup QR code, shown in the order detail with the pickup session (time and place).
  • Remove address_id, delivery_fee, the shipped / delivered states and the tracking number.
  • Record the decision in the brief (Scope and Schedule risk).

Payment

  • Payment happens on Ztor's payment page (a redirect), never on the site, so the site never handles card details.
  • The flow: payment methods for this cart → quote → submit → payment page → back to the site → check the result.
    • Submit returns a pending status and the payment page URL. It never returns paid.
    • The payment page stays valid for up to 10 minutes.
    • If a payment fails, the fan can pay again for the same order.
  • The site sends a payment method code from the list (card, Apple Pay, Google Pay, …), not a card token like pm_x92. Which methods appear depends on the fan's currency.
  • Endpoints to add: payment methods for this cart · pay again. Quote and payment result are already listed in section 2.
  • Remove "Antom sandbox" from Environments and "Payment via Antom (capture at order)" from Integrations. The payment provider sits behind Ztor's gateway and isn't the site's concern.

Prices and totals

  • Totals are the subtotal and the amount payable. There's no delivery fee or tax line.
  • Discount codes are out of the first cut, so remove discount and promotion from orders.
  • Sale prices do exist in the eShop (original vs current price), so a product can show both.

Order states

  • Order history shows paid orders only: paid → completed (collected at pickup).
  • Cancellation is an ops void in Creator Studio. How a voided order appears to the fan is being confirmed with the dev team.
  • No refunds in the product. A fan who wants one emails support, and ops handle it manually. The site shows the refund policy and how to get in touch.
  • No guest checkout: fans sign in before adding to the cart. With No crossover on, that's a site account.

What changes on the site (for the site team)

As of the 09-14 review, lloud.club's checkout was built for delivery: address form, flat shipping fee, 5% tax line, promo codes, saved card. For launch it needs:

  • a pickup contact instead of the address form
  • no shipping fee, tax line or promo field
  • no saved card, because payment happens on Ztor's page
  • the pickup QR and session on the order page

4. Sign-in

A Ztor sign-in page (SSO): the site never handles passwords

  • Sign-in happens on a Ztor-hosted page showing the Ztor logo and the site's name. The site sends the fan there and gets them back signed in, so passwords are never typed on an artist's site.
  • The page handles: sign-in, registration, social login, email verification, password reset and change, and account deletion. These replace POST /auth/register, /auth/login and /auth/social.
  • The flow (OAuth 2.0 authorization code + PKCE, the standard for browser-only sites):
    1. The site sends the fan to the Ztor sign-in page with its channel ID, its return URL, a random state and a PKCE challenge.
    2. The fan signs in or registers, with email + password or a social account.
    3. The page sends the fan back to the site's return URL with a one-time code.
    4. The site exchanges the code for tokens with POST /auth/token, and gets an access token (1 hour) + refresh token.
    5. Refresh: POST /auth/token with the refresh token. Each refresh issues a new refresh token, and reusing an old one signs the fan out.
    6. Sign out: POST /auth/logout revokes the refresh token and ends the sign-in page session.
  • Return URLs must be on the site's allowlist, set in Creator Studio.
  • No crossover: the sign-in page knows which site it's serving.
    • On a No crossover site it only signs in that site's accounts, and new registrations create accounts for that site.
    • Because the page shows the Ztor logo, its copy should tell fans that site accounts are separate from ztor.com accounts.

Social login (required at launch)

  • Social login runs on the Ztor sign-in page. Each provider therefore needs only Ztor's sign-in domain registered, not each artist site. Each site's return URL goes on its allowlist in Creator Studio instead.
  • Providers: the four ztor.com supports today: Apple, Google, Facebook, LINE. LINE matters for fans in Thailand and Taiwan. Replace v1.4's "Spotify, Apple, Google" default.
  • On a No crossover site, a social sign-in creates or uses that site's account.
  • Remove POST /auth/social {provider, id_token}. The ya29… sample is a Google access token, which can't prove who the fan is.

Registration

  • Market (country) comes from the fan's IP address, set by the server. Remove market from the request.
  • Language is chosen at registration (English by default on LLOUD) and can be changed in the profile. Account and order emails use it; without it they fall back to Traditional Chinese (zh-hk).
  • Terms: the fan accepts Ztor's terms of sale and privacy policy, because Ztor is the seller and payment goes through Ztor's gateway. The site's own terms are added if it has any.
  • The email address is verified after registration.

Profile

  • Keep: GET /me and PATCH /me (name ≤ 40, bio ≤ 160, plus language). A profile update can never change tier, points or membership (AC-2.4).
  • Add PUT /me/avatar: the fan uploads their own photo (JPEG or PNG, ≤ 5 MB) and gets back the avatar URL. v1.4's only upload endpoint was admin-only and has been removed. Update AC-2.3 to match, dropping "JPEG data URI".

6. Currency

  • Creator sites follow the same currency rule as ztor.com. The Creator API has no currency rule of its own.
  • The rule (Ztor's, from eShop 2.2): the fan's currency is fixed at registration from their IP.
    • Singapore → SGD, Hong Kong → HKD, Taiwan → TWD, everywhere else → USD.
    • It doesn't change when the fan travels or uses a VPN.
  • Ztor's systems set the fan's currency; the site can't choose it. The site reads it from the currency-context endpoint (section 2) and shows exactly what Ztor quotes, so the price shown and the price charged can't differ.
  • Supported currencies: SGD, USD, HKD, TWD.
  • Remove "channel currency" everywhere: the Money decision ("decimal in the channel currency"), Channel.base_currency, and the channel currency in samples.
  • Money format: every amount carries its currency code, and all amounts use one format. TWD has no decimal places.

7. Gating

Launch: no new service

  • Keep GET /entitlements?product=, which answers "can this fan buy this now, and if not, why?".
  • At launch the answer comes from the eShop's own facts: sale start (not buyable before the sale opens), purchase limit (per fan, across orders) and stock. The eShop also enforces these at checkout.
  • Reasons at launch: not_on_sale_yet · purchase_limit · sold_out. Checkout returns the same reason when it refuses, so the site shows one message (AC-3.2).
  • No region lock for now. No crossover already keeps the creator's products on the site.
  • Remove from the Policy rules section for launch:
    • purchase_limit and inventory: the eShop enforces them.
    • region: not needed now.
    • member_only: every buyer is a signed-in site member.
    • tier, presale_window with a tier, and points_min: these need tiers and points.
  • GET /me/entitlements moves to category 3.

Next step: the Policy service (after launch, before tiers and points)

  • Not in the current sprint. Build it before tiers and loyalty points go live.
  • It sits behind the same /entitlements endpoint, so the site doesn't change; it just starts returning new reasons, e.g. tier locked.
  • It adds:
    • the rule format (all / any, typed conditions)
    • rules set up in Creator Studio
    • tier and lifetime-points conditions, taken from Ztor's own scoring
    • early access for top tiers
    • the same checks on ztor.com's own checkout
  • Reward and vault unlocks: decide with the loyalty vendor, which may own tier benefits.
  • Keep v1.4's Policy rules section as the design input for this step, marked "next step".

8. Acceptance

The four criteria

  • 01 — keep. The platform owns data and transactions, never presentation.
  • 02 — reword. Sign-in and payment now happen on Ztor's pages by design, so "curl can complete the entire flow with no browser" can't pass any more. The criterion's purpose, that the site decides nothing, stays:

    02 · The site decides nothing — the server enforces every rule. With a test token (staging), curl calls the same endpoints the site calls — can-I-buy → add to cart → quote → submit — and gets the same answers and refusals. Calling an endpoint directly can't get past a rule the server refuses. Sign-in and payment happen on Ztor's pages by design and sit outside this test.

  • 03 — keep. Adding an artist requires no new endpoints.
  • 04 — reword: "Each site sees only its creator's data, and every order records the site it came from." Drop the ztor.com / tyson.com example.

Rewrite the curl sample with these steps (every call carries X-Channel-Key + Bearer):

  1. GET /v1/entitlements?product=… for a product whose sale hasn't opened → allowed: false, reason: not_on_sale_yet
  2. POST /v1/cart/items {skuId, quantity} for that product → refused with not_on_sale_yet. The server refuses; the site's code isn't involved.
  3. For a product that's on sale: POST /v1/cart/items → POST /v1/checkout/quote → POST /v1/checkout → pending + a payment URL.

Keep the closing test: "can the next artist's site be built without touching the API repo?"

Clean-up

  • Product payloads:
    • Remove points_award and unlocks; they're category 3.
    • Include full image URLs, with CDN sizes, in the product, so the site doesn't fetch images one by one. Product images are uploaded in Creator Studio. The eShop sometimes returns relative image paths, so the Creator API always returns full URLs.

Depends on the dev team (for awareness; I'm raising these with Eric)

  • A Ztor sign-in page (SSO) is launch-critical, because sign-in comes first. The dev team needs to build:
    • the hosted pages: sign-in, registration, social login (Apple, Google, Facebook, LINE), email verification, password reset, account deletion
    • POST /auth/token for code exchange and refresh
    • a per-site return-URL allowlist
    • the No crossover rule on the page
    • the four providers registered for the Ztor sign-in domain
  • No crossover is launch-critical, because LLOUD launches with it on.
    • Accounts in Ztor's identity need the per-site no-crossover rule: the same email can register on the site and on ztor.com, and each account signs in only where it belongs.
    • Shopping and Order must still accept those fans' orders.
  • Per-site product listing. With No crossover on, the creator's products must be hidden from ztor.com yet still listed on the site. The eShop's single visibility flag can't do both today.
  • No shop filter. Shopping has none on products or orders, and the Creator API needs one to show only the site's own items.
  • Orders don't record which site they came from.
  • The post-payment return URL isn't checked, so the Creator API must enforce each site's allowed return URLs.
  • Catalog responses aren't cached, so drop-day traffic needs caching and limits in the Creator API layer.
  • Unpaid orders hold stock. Stock is taken when the order is created, before payment, so on a hot drop an unpaid order holds stock for up to ~10 minutes. Confirm stock is released when a payment expires.
  • Voided orders: how they show in the fan's order history.
  • If management picks branded emails: a per-site sender (the creator's email domain verified for sending) and the creator's logo on account and order email templates.
  • eShop rule to confirm: is there a scheduled sale end? (The purchase limit is per fan, across orders.)
  • Next step (not this sprint): the Policy service, built before tiers and loyalty points go live.
