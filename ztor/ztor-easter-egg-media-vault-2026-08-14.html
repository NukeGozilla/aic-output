Core concept (shared by both sides)

  • A creator owns multiple vaults (庫房). Each vault = a themed collection of exclusive media (photo / video / audio / text post) behind a door.
  • The door opens via any of several paths: automatic conditions (tier, purchase, backing, attendance, achievement, mission/task) or a hand-issued key (bearer credential — gift link or NFC product).
  • The number the creator cares about: “Who gets in” — how many fans can open this vault right now. Computed as a true set union over a fan population (conditions ∪ claimed keys, overlap deduped), never by adding counts.
  • Access semantics: tier conditions are volatile (re-evaluated on the nightly tier recompute; a fan who drops tier keeps access until tonight 00:00 — “grace”), while purchase / backing / event / achievement / mission conditions are permanent (they record something that already happened — access never expires).
  • Keys are a second road on top of conditions: single-use gift link (“first fan to open it keeps the access”) or an NFC batch (N uses written into a keychain/furniture product; fan taps phone → gets access). Keys can be revoked (leak brake) — revoked keys stay visible in history (“issued, revoked, 12 had claimed”).
  • Social proof: each item/vault shows how many keys are out (“X 人已解鎖”), deliberately on a decreasing curve for rarity.

CS side — how the creator sets it up (Media Vault)

Master–detail single page under Fans: left rail = vault list (cover / name / key-count = current reach), right = selected vault.

Setup flow per vault:

  1. New vault (button above the rail list) → inline name field.
  2. Unlock conditions — chips added from a catalogue popover, grouped: Tier ≥ X · Bought (specific product, incl. limited runs) · Backed (specific co-create project) · Attended (specific event/ticket) · Earned (achievement: Hall of Fame, Ztor Score 800+, 12-month streak). Rule structure (PG-025, not yet in documents/): rules = [ {items:[cond, …]}, … ] — outer OR of “methods”, inner AND within a method (“Superfan AND bought vinyl” OR “attended signing”). Empty method never matches.
  3. “Who gets in” — sticky live readout: N of total fans, with a per-tier breakdown bar; changes instantly as conditions are edited. Reach math is set-based over a seeded 1,283-fan population; capped conditions can never exceed real sold counts (e.g. 1/50 vinyl sold 21 → cap 21).
  4. Issue a key (drawer): choose Send to one fan (single-use gift) or Make an NFC product (batch with uses count, linked to a shop product); generates human-readable code (KC26-A4VP, no 0/O/1/I — laser-engravable) + link ztor.com/k/<code>. Below: Keys issued list with claimed/total per key + revoke.
  5. Share page — copies a public showcase-page link for the vault (that page itself is spec’d “later”; entry + copy flow only).
  6. Upload media into the vault (one picker; grid auto-sections photos → clips → audio). Per-item settings drawer = preview, rename, delete + facts only (permissions/expiry/watermark deliberately NOT invented — no upstream spec).
  7. Viewer lens — “View as: Fan/Ranked/Superfan/Inner Circle” swaps the whole page to that tier’s perspective (locked vaults dimmed in rail, gated mask over content).

Tiers referenced (from tier-settings): Inner Circle · Superfan · Ranked fans (devoted) · Fan.

FE side — what the fan sees (彩蛋解鎖 / Unlock Surprises)

Page = per-creator vault hub (?c=<creator-slug>, profile from ZTOR_CREATOR_PROFILE). Creator identity bar links to profile + their shop. Left rail = 彩蛋列表 (vault list with lock icon until first unlock, then progress n/total); right = selected vault’s items + unlock conditions. Per-vault progress bar (“你已解鎖 n / N”).

Item states (kind in seed): perm (mission/task-earned permanent key), level (tier-gated, nightly recompute), open (public). Card shows: blurred media + lock, filename as teaser when locked (title revealed when unlocked), type chip, condition text with key icon (“拿什麼換鑰匙”), social-proof count, and a CTA button for task conditions.

Mission/task condition types in the demo ladder (10-item difficulty climb in vault 1):

  • Follow + join community
  • Share the vault page to 3 friends
  • Share a designated post to 10 people
  • Invite 3 friends to the community
  • Tier ≥ Fan / Superfan / Inner Circle (level kind)
  • Watch a designated film OR attend a Watch Party
  • Buy any merch in the shop
  • Cumulative popcorn tipping ≥ 500
  • Attended a specific event (成就; “補登票根” retro ticket-claim CTA)
  • Backed a specific co-create project
  • 大彩蛋 (grand egg): new single full version, 72-hour early listen — Inner Circle only, orange-glow treatment + “大彩蛋” tag

Unlock interaction: CTA click → burst animation on the lock → toast “條件達成——鑰匙已發給你” → card flips to unlocked; state in localStorage ztor_vault_v1 (demo only — real completion of the mission isn’t verified).

View modes (0806 Dolly rulings): only two — 一般用戶 (new fan, rank 0, all locked) and 創作者本人. Creator view on FE is information-only: no manage buttons, no “new vault”, uncensored content + key counts per item/vault, plus a banner “管理在 Creator Studio”. All management lives in CS.

Divergences / open items to reconcile before a BRD

  1. Naming: CS calls it Media Vault; FE calls it 彩蛋解鎖 / Unlock Surprises. Fan-facing framing is missions→keys; CS framing is audience-gating. One feature, two vocabularies — needs a canonical name pair (EN/ZH).
  2. Mission conditions exist only on FE. CS condition catalogue = tier / bought / backed / attended / earned. FE adds social/growth missions (share page ×3, share post ×10, invite ×3, join community, watch film / watch party, popcorn tipping ≥500). CS has no UI for defining these mission types yet — the biggest CS gap.
  3. Mission verification is unspecified (demo unlocks on click). Share/invite counts, watch completion, tipping totals all need real tracking + anti-abuse rules.
  4. Rule semantics: CS supports OR-of-AND-groups (PG-025, awaiting product ruling, in ASSUMPTIONS.md); FE demo is one condition per item. Also note granularity: CS gates at vault level, FE gates per item — per-item conditions vs per-vault door needs an explicit decision.
  5. Keys on FE: gift-link/NFC claim flow (ztor.com/k/<code>) has no fan-side page in the FE demo.
  6. Share page (public vault showcase) has an entry point in CS but no spec/page anywhere.
  7. Grace rule (drop tier → keep until 00:00) is encoded on both sides — consistent; surface copy exists (“權限保留至今晚”).
  8. Fan-side numbers are seeded mock data (1,283 fans etc.); FE keys counts are curated for a rarity curve, not computed.
