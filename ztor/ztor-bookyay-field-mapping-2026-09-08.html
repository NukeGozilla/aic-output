2026-09-08 · English version 2026-09-09 · from the 09-08 standup (CS already covers most Bookyay fields; FE not yet aligned) · parent rule: BRD v1.3 §6b / BR-10 · tick row by row at the 09-09 meeting

rev 09-09: legend added (from BR-10) · 8 review fixes — authority labels unified · event type / lineup / event status split by authority · QR payload and scan status flagged as ticket-level feeds · change-notification markers on date, doors, venue · T&C row · series/show sequence promoted to Must pull

Three questions, answered per field: ① Pull it from Bookyay? ② Where does Ztor use it (FE buyer pages / CS admin)? ③ Who is the authority (feed-locked / feed · override allowed / Ztor-owned)?

Legend 圖例 — Pull? 拉取

ValueMeaning
Must pull 必拉Required for Phase 1 — a Ztor surface depends on it
Recommended 建議拉Useful now or soon; not blocking
Optional 可略May be skipped; harmless if pulled and unused

Do not pull 不拉Out of Phase 1 scope

Legend 圖例 — Authority 權威 (rule source: BRD v1.3 BR-10 / §6b)

One test decides every row: if the ticket, venue scan, money, or lifecycle depends on the field → Bookyay-owned, locked (an override would make the buyer’s ticket disagree with the systems that validate it). If it only affects how the Ztor page looks → Ztor-side. Per the 09-09 meeting we are converging on image-only override (all data fields locked); CS shows per-field sync state (follow-feed / overridden, one-click revert).
判準只有一條：票券・掃描・金流・生命週期依賴的欄位 = Bookyay 鎖定；只影響 Ztor 呈現的 = Ztor 側。09-09 傾向收斂為僅 image 覆寫（資料欄位全鎖）。
ValueMeaning
feed-locked feed 鎖定Bookyay is the source of truth. Ztor shows the value read-only; every hourly sync overwrites it. Never editable on Ztor.
feed · override allowed feed，可覆寫Bookyay supplies the default value. A CS admin may override it for Ztor UI needs. An overridden field stops tracking the feed; one-click revert restores the feed value. Candidate fields: display name, description, lineup display — 09-09: converging on image-only override; pending Bookyay ops confirm.
Ztor-owned Ztor 自建Never comes from Bookyay (section E).
—Not pulled or not shown, so no authority applies.

rev 09-09：加圖例（依 BR-10）· 審閱修正 8 項 — 權威標籤統一 · 活動類型／Lineup／活動狀態拆分權威 · QR payload 與掃描狀態標為票券層級 feed · 日期／doors／場地加變更通知標記 · 新增 T&C 列 · 系列／場次序升為必拉

三個問題，逐欄位回答： ① 要不要從 Bookyay 拉？ ② Ztor 端用在哪（FE 買家頁 / CS 管理）？ ③ 誰是權威（feed 鎖定 / feed，可覆寫 / Ztor 自建）？

圖例 — 權威 （規則來源：BRD v1.3 BR-10 / §6b）

值意思
feed 鎖定Bookyay 是唯一權威。Ztor 唯讀顯示，每小時同步一律覆蓋；Ztor 端永不可編輯。
feed，可覆寫Bookyay 提供預設值，CS Admin 可為 Ztor UI 需要覆寫。覆寫後該欄位停止跟隨 feed；一鍵還原 feed 值。 只有三個欄位適用：顯示名稱、描述、Lineup 顯示。
Ztor 自建不來自 Bookyay（E 節）。

A · 基本資訊

欄位拉取？Ztor 用途權威備註
event id必拉對帳鍵（匯入 / 回寫 / 作廢）feed 鎖定同一場只帶入一次的鍵
活動名稱必拉FE 卡片+詳情 · CSfeed，可覆寫（顯示名稱）BR-10
活動類型必拉FE 分類篩選 · CS 標籤feed 鎖定（來源值）· FE 三分類對應表 = Ztor 自建線上演唱會 / Watch Party 歸屬 = 週三決策 #3
描述必拉FE 詳情feed，可覆寫Ztor UI 版面不同（09-08：欄位調整以符合 UI/UX）
主辦方名稱必拉CS 對應創作者的線索feed 鎖定無 creator 檔案 — 僅文字
Lineup / 表演者必拉FE 詳情feed，可覆寫（顯示文字）· Ztor 帳號連結 = Ztor 自建
系列 / 場次序必拉FE 場次選購 · CSfeed 鎖定09-08：多場次選購是 FE 需求 → 必拉（原「建議拉」）
條款 / 退票規則連結（T&C）建議拉FE 詳情 · 結帳feed 鎖定BR-14 沿用 Bookyay 條款 — 請 Jesse 確認 feed 是否帶條款 URL

欄位拉取？Ztor 用途權威備註
