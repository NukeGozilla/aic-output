05Six decisions the Sep 21 freeze needs9/21 凍結前要定的六件事

Without these, the freeze is a date on a calendar. Each one changes what Eric's team builds in Golden Week. 沒有這六件事，凍結只是日曆上的一個日期。每一件都會改變印尼團隊在假期裡做什麼。

01 · fulfilment
How does a LLOUD order reach the fan?LLOUD 訂單怎麼送到粉絲手上？
lloud.club is a fashion drop with shipping; eShop 2.2 is pickup-only. Pick: shipping into 2.2/2.3 · pickup / pop-up only · Beamco-managed fulfilment.lloud.club 是要寄送的服飾發售；eShop 2.2 只有取貨。三選一：寄送排進 2.2/2.3 · 只做取貨／快閃 · Beamco 代出貨。
02 · facade + payment
Who owns the public gateway and checkout?對外閘道與結帳歸誰？
Proposal: Eric's team owns the facade; eShop / Bookyay expose internal APIs only. Also: does Lisa's site settle to a separate payment account (order tagging)?提案：Eric 團隊負責 facade，eShop／Bookyay 只開內部 API。另外：Lisa 網站是否用獨立收款帳號（訂單標記）？
03 · open loyalty
Can Open Loyalty run our scoring model, and who owns loyalty?Open Loyalty 能跑我們的計分模型嗎？誰負責積分？
On the call: percentile tiers + 45-day decay, per-creator programs under one contract, "active member" definition in writing. Contract by Oct 23 or release 4 misses Nov 20. Sync-back to Ztor stays ours.通話確認：百分位等級＋45 天衰減、單一合約下的每創作者方案、「活躍會員」定義白紙黑字。10/23 前簽約，否則 release 4 趕不上 11/20。同步回 Ztor 仍由我方做。
04 · cs team scope
Does the CS team take Creator API groups too?CS 團隊是否也接 Creator API？
They carry eShop 2.2 through UAT and production to Oct 30. Adding API groups on top puts release 2 at risk; Creator API stays with Eric's team.他們要扛 eShop 2.2 的 UAT 與正式上線到 10/30。再加 API 會拖累 release 2；Creator API 留在 Eric 團隊。
05 · cdn / domain
Is a store.com image origin acceptable at launch?上線時圖片來源顯示 store.com 可接受嗎？
Whitelist now (origin visible in the inspector only); custom CDN domain later if Lisa wants the link hidden.先用白名單（只在開發者工具看得到來源）；若 Lisa 要隱藏關聯，之後再做自訂 CDN 網域。
06 · not in eshop yet
Promo codes, micro-donations (微捐), region lock — in release 2?折扣碼、微捐、地區鎖——進 release 2 嗎？
None exist in eShop today. Recommend out of release 2; region lock only if it is already in 2.2. Official promo codes are being scoped with ops separately.eShop 目前都沒有。建議不進 release 2；地區鎖除非 2.2 已有。官方折扣碼正另與營運確認需求。
⚠
Single point of failure: design, site build, integration and acceptance of lloud.club all sit with L. Give L the frozen spec on Sep 25 and mocks, so the build starts before release 1 exists — the same move that saved the 2.1 schedule. 單點風險：lloud.club 的設計、建站、串接、驗收都在 L 一人身上。9/25 把凍結的 spec 與 mock 交給 L，讓建站在 release 1 之前就開始——這正是 2.1 時程救回來的做法。

06Option B — lloud.club integrates Open Loyalty directly選項 B——lloud.club 直接串接 Open Loyalty

Plan A routes loyalty through Ztor: Open Loyalty → Ztor → release 4 → lloud.club, live on lloud.club Dec 7. If L must ship loyalty by end of November, lloud.club can call Open Loyalty directly while Ztor does its own integration in parallel; lloud.club moves onto release 4 later. Live Nov 27, decoupled from release 4, at the cost of a second integration and the five items below. 方案 A 的積分經 Ztor 中轉：Open Loyalty → Ztor → release 4 → lloud.club，lloud.club 於 12/7 上線。若 L 必須在 11 月底前推出積分，lloud.club 可直接呼叫 Open Loyalty，Ztor 同時做自己的串接；lloud.club 之後再改接 release 4。11/27 上線、不受 release 4 牽制，代價是多一次串接與下列五件待解。

B1 · identity
Who creates the Open Loyalty member?誰建立 Open Loyalty 會員？
Member id = Ztor user id, created by Ztor at sign-in. lloud.club never creates members, so one fan is one member across ztor.com and every creator site.會員 id＝Ztor user id，由 Ztor 於登入時建立。lloud.club 不建會員，一個粉絲在 ztor.com 與所有創作者網站只有一個身分。
B2 · one writer of points
Orders live in Ztor eShop, so who posts them to Open Loyalty?訂單在 Ztor eShop，誰把它們送進 Open Loyalty？
Ztor posts order and refund events; lloud.club only reads balance, tier and ledger, and submits mission proofs. This is Eric's desync warning: two writers means bought-but-not-credited.由 Ztor 送出訂單與退款事件；lloud.club 只讀餘額、等級、帳本，並提交任務證明。這正是 Eric 提的不同步風險：兩個寫入方會出現「買了卻沒加分」。
B3 · keys
Can a browser-side site hold Open Loyalty credentials?前端網站能拿 Open Loyalty 金鑰嗎？
Not the admin key. Needs per-member tokens from Open Loyalty's customer API, or a thin Ztor proxy endpoint. Confirm on the vendor call.不能拿 admin key。需要 Open Loyalty 客戶端 API 的會員層級 token，或由 Ztor 提供輕量代理端點。通話時確認。
B4 · sync-back
Gating and the Media Vault need points and tier inside Ztor購買限制與媒體庫需要 Ztor 內有積分與等級
An Open Loyalty → Ztor webhook (points, tier changes) feeds the Policy service. Needed in Plan A too, so it is not extra work, but it sits on the Nov 27 path.Open Loyalty → Ztor 的 webhook（積分、等級變更）餵給 Policy 服務。方案 A 也需要，不算額外工作，但落在 11/27 的路徑上。
B5 · migration + ops
Two integrations until lloud.club moves to release 4在 lloud.club 改接 release 4 之前要維護兩套串接
Ops sees LLOUD loyalty in Open Loyalty's admin, not Creator Studio, until the migration (Dec–Jan). Any rule change is made twice.遷移前（12 月至 1 月）營運要在 Open Loyalty 後台看 LLOUD 積分，而非 Creator Studio。規則改動要做兩次。
verdict
Saves ~10 days on lloud.club; adds risk on Ztor's sidelloud.club 省約 10 天；風險移到 Ztor 端
Worth it only if Nov 27 is a hard business date for Lisa. Otherwise Plan A (Dec 7) is one integration, one admin, and no migration. Decide after the Open Loyalty call answers B3.只有在 11/27 是 Lisa 的硬性商業日期時才值得。否則方案 A（12/7）只有一次串接、一個後台、不用遷移。等 Open Loyalty 通話回答 B3 後再決定。
