Operating model

Three boards, one spine

The feature catalog, the release plan, and the engineering board are three Asana projects sharing one Feature task. The AI dev workflow's 5 stages are not a fourth board — they're tracked by the existing Status field on the Roadmap. Multi-homing + subtasks keep it all in sync with zero duplication.

What · Feature Board (project) When · Roadmap (project) How / who · Dev board (project) Where · Status (existing field on the Roadmap)

01 The spine & the four lenses

One Feature task is created once and never duplicated. It surfaces in each board with a different grouping. Three boards are separate projects (a task can hold one section in each); the process stage is a shared field; dev work is subtasks.

02 The 5-stage gated pipeline — a relay, not a free-for-all

The Status field carries each feature through the relay (the Asana value is shown in the strip below). BA-led front, designer shepherds the build, formal QA at the end. Two gates force a sign-off before work compounds downstream.

VERIFY GATE All four must pass before shipping
  1. Dev self-test against the BRD checklist
  2. AI-generated test cases from acceptance criteria, via Playwright
  3. Designer review — visual / UX fidelity vs. prototype
  4. BA approval of business-critical flows

03 Two sources of truth — the spec contract

Put both in the Feature task description so they travel with the card to every board, and QA tests straight against them. (Kept out of dedicated fields to keep the field set lean.)

Prototype URL
Authorizes the UI & flow
Appearance, screen order, which design-system components. Owned by Designer + BA.
BRD URL
Authorizes the logic
Business rules, permissions, error / loading states, edge cases, acceptance criteria. Owned by BA.
