Decisions Needed — April 1 Meeting

1. Film Upload Feature Ownership

The film upload feature currently sits in Eric's codebase. Eric has suggested he continue owning it since it's already integrated with his pipeline. However, this feature also depends on Ztor's existing Back Office approval workflow — creators cannot publish directly; content must go through team review before going live.

If Eric keeps it, Kerry's Creator Studio calls Eric's upload API (cross-team dependency), and the BO approval flow stays intact. If Kerry takes it, the upload migration is larger upfront and the approval workflow must also be ported or integrated via API.

Eric keeps upload + approval Kerry takes over (incl. approval) Kerry owns upload, BO approval stays with Eric
Decision: Jeff + Eric + Kerry

2. Unified User Database — Team Ownership

Store and Bingo (Bookyay) user databases need to merge into one unified model. The complication: Kerry's team already built the foundation for Bookyay and understands its data model, but Eric currently owns both the Ztor and Bookyay user databases in production.

This is critical path — most Phase 1 features depend on a single user model. Whoever owns this must handle the migration without breaking either platform.

Eric owns (already has both DBs) Kerry owns (built Bookyay foundation) Joint migration, Eric owns final DB
Decision: Jeff + Eric + Kerry

3. Large File Upload Strategy (>1GB)

Browser uploads break above ~1GB. AI-generated films could hit multi-GB sizes. Need a solution that doesn't force creators to leave the platform.

Desktop app with resume Browser <1GB / app >1GB Browser-only for Phase 1
Decision: Eric (technical feasibility)

4. Payment Infrastructure — Gateway + Ownership

Gateway: Replace Stripe with 2C2P for non-crowdfunding payments? Two approaches: hosted redirect (simpler, worse UX) vs full API integration (more work, better UX). Sam evaluating if 2C2P covers CC + Google Pay + Apple Pay globally.

Ownership: Which team owns the payment layer going forward? Today it's in Eric's codebase, but Creator Studio adds new touchpoints (payouts, crowdfunding, content purchases).

Eric owns (shared svc) Kerry owns (creator backend) Standalone microservice
Decision: Jeff + Eric + Kerry · Sam confirms 2C2P feasibility

5. Event Migration Priority

Events must exist in Store 2.0 before Bingo can shut down. Bookie's event system includes seating charts (座位表) and complex ticketing — significant migration, not a simple port. E-Shop and Events cannot be simultaneous.

Phase 2 (sooner) Phase 3 (later)
Decision: Business (Jeff + stakeholders)

6. Beamco Artist Portal Codebase Inheritance

Creator Studio inherits the Beamco Artist Portal codebase. The dev team has flagged that the existing codebase needs refactoring before it can scale into Creator Studio's scope. Two paths forward — and each has very different timeline and risk implications:

Option A: Refactor the existing codebase end-to-end. How long would this take? Does the team have a realistic estimate, or is this an open-ended effort that will bleed into Phase 1 delivery?

Option B: Keep the existing backend and convert it into microservices (the backend logic is reusable), but build the frontend fresh for Creator Studio. This avoids the frontend refactor trap and lets the team ship a clean UI on top of proven backend services.

Full refactor (timeline TBD) Backend → microservices, new frontend Ship as-is, refactor later
Decision: Kerry's team (technical assessment) + Jeff (timeline impact)

7. Microservice Architecture Design

The ownership map defines which team owns which service, but several architectural decisions still need alignment before development begins:

Service boundaries: Are the current service boundaries the right cut? E.g., should Auth/Identity and the Unified User DB be one service or two? Should Crowdfunding and NFT/Mint be merged since minting is triggered by crowdfunding participation?

Communication patterns: The plan calls for Kafka async events + sync HTTP via Gateway. What's the latency budget for sync calls? Do we need a saga orchestrator for multi-step flows (e.g., crowdfunding → payment → NFT mint)?

Deployment & infra: Containerized (K8s) or serverless (Lambda/Cloud Run)? Mono-repo or poly-repo? CI/CD pipeline ownership per team or centralized?

Observability from day one: Distributed tracing (OpenTelemetry), centralized logging, health checks — who sets up the shared observability stack?

Discuss at Apr 1 meeting Separate tech design session Eric + Kerry propose independently
Decision: Eric + Kerry (technical leads) + Jeff (prioritization)

Hard Architectural Rules

→ No app calls a service directly — all through Gateway

→ No service reads another service's DB — API contract only

→ Every revenue event hits the waterfall — no bypasses

→ Compliance freeze: no override without CEO + Legal

→ Core services are consumers only — never call app services back

→ Revenue ledger and audit store: INSERT only, zero deletes ever

→ Config Version CI locked at event creation — immutable

→ mTLS between Gateway and all services — services not public-facing
