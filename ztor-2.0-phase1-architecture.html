Architectural Rules

Carried forward from the dev handoff. These are the invariants the foundation must uphold.

No app calls a service directly — all traffic flows through a Gateway.
No service reads another service's DB — API contract only.
Every revenue event hits the Waterfall — no bypasses.
Compliance freeze: no override without CEO and Legal.
Core services are consumers only — they never call business services back.
Revenue ledger and Audit store: INSERT only, zero deletes ever.
Config Version locked at event creation — immutable forever.
Gateway auth is app-token only; user identity stays inside services.

01Auth issuing service ownership

The dev handoff specs POST /oauth2/token as "an independent auth service" but doesn't name an owner. Indo team is the default in this doc — needs confirmation. Also: where does the issuing service itself live (which gateway / which deploy)?

Indo owns end-to-end Co-build with China during transition Third-party (Auth0 / Cognito)

02V1.0 → V1.1.0 migration path

The dev's gateway docs are versioned V1.1.0 — implying a V1.0 exists. Is there a live gateway in production today that needs cutover, or is Phase 1 greenfield on the new stack? Cutover risk needs a runbook before we lock the timeline.

Greenfield — confirm with dev team Cutover required — needs runbook
Decision · Eric + dev team

03Crowdfund-only Kafka topics

If Revenue Event service is Phase 2+, Crowdfunding emits revenue events directly. We need to confirm the topic contract (crowdfunding.participated vs a generic revenue.event) so Waterfall doesn't need rework when the generic service ships.

Emit both — denormalized Generic schema from day one Crowdfund-specific, refactor later
Decision · Kerry + Indo (Waterfall lead)

04Large file upload strategy (>1GB)

Carried over from April. Not blocking for Crowdfund-only Phase 1, but blocks Phase 2 Content. Worth resolving now so the Indo team can pre-position infra (S3 multipart, resumable, etc.).

Desktop app with resume Browser <1GB / app >1GB Browser-only, defer to P2
Decision · Eric (technical feasibility)

05Payment — 2C2P vs Stripe (non-crowdfund flows)

Stripe stays for Crowdfund (locked). 2C2P evaluation continues for future flows — pure Phase 2+ concern, but the gateway and payment-service shape we build for Crowdfund should not paint us into a corner.

Stripe-only abstraction P1 Provider-agnostic interface from day 1
Decision · Jeff + Eric + Kerry · Sam confirms 2C2P

06Production capacity targets per gateway

QPS limits in the dev docs (100 / 500 / 1000) are illustrative. We need real targets per gateway before sizing the Consul, Redis and Kafka clusters. Crowdfund launch volume is the binding input.
