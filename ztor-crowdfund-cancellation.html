Project Cancellation Flow Biz overview

How a crowdfund project gets cancelled — what ops does, what the system does automatically, and how backers get their money back.

🛑 Cancellation is a manual ops decision — the system never cancels a funded project on its own. Ops clicks a button in the back office, an email auto-fires to every backer, and then ops processes the refunds in Stripe in one batch.

Most projects never need this flow. But when a project does have to be pulled — creator can't deliver, compliance issue, payment recovery exhausted — we need a clean way to shut it down, tell backers, and return money already collected. This page covers the three things product needs to deliver to support that flow.

When ops considers cancelling

Cancellation is always a judgment call — the trigger is upstream, the cancel itself is manual.

Upstream triggers · ops reviews
⚠
Payment recovery exhausted. Both 7-day windows expired with too many failed charges to proceed.
⚠
Creator default. Creator withdraws, can no longer produce, or breaches the agreement.
⚠
Production failure. Project enters production but cannot deliver the planned content.
⚠
Compliance / legal. Content issue, IP dispute, or regulatory flag during or after funding.

One button, one email, one batch refund. Each row below is a product deliverable.

Three product deliverables

SC-03 scope. Together these cover the cancel flow end-to-end — from the back-office button to the refunded backer.

① · Back office

Cancel project button

New action in the back-office project editor. Ops selects a reason (recovery failed / creator default / production failure / compliance) and confirms. The project transitions to the canceled terminal state and is locked from further changes.

Build: back-office UI
② · Auto-trigger

Cancellation email to backers

The moment the project flips to canceled, the system fires an email to every backer explaining the cancellation and that a refund is on its way. No manual sending — ops doesn't have to write or forward anything.

Build: notification template + trigger
③ · Manual

Stripe batch refund

Ops opens Stripe's back office and refunds the affected charges in one batch operation. Manual on purpose — ops decides scope (full refund, partial, etc.) and confirms in Stripe directly. No automated refund job inside our app.

Build: none (use Stripe UI)

📅 Step-by-step from a backer's point of view

Before
Backer has pledged and either the charge has already cleared (project was funded) or is queued for batch charge at campaign close.
Day 0
Ops cancels the project in the back office. The project state flips to canceled. The backer doesn't see this directly yet.
Day 0 · seconds later
Cancellation email arrives. Backer learns the project has been cancelled and that the refund is being processed.
Day 0 → 3
Ops processes batch refunds in Stripe. Manual, but done in one batch — not one card at a time. Stripe sends each backer its own refund confirmation.
Day 3 → 10
Funds return to the backer's card. Settlement time is set by the issuing bank, not by us — typically 3-10 business days.
After
Project stays visible in the backer's profile with a cancelled / refunded status. No further action from the backer.
Scope note — SC-03 in the BRD. Product only builds ① the back-office cancel button and ② the auto-cancellation email. ③ the refund itself is operated by ops directly in Stripe — no in-app refund UI, no automated refund job. Decision criteria (when to cancel, when to keep running) sit with ops, not the product.
