End-to-end workflow — 4 phases, two biz & ops gates

Two Biz & Ops gates wrap engineering — Design + Copy sign-off at gate 5, then implementation validation at gate 12. Approval rule: Sam or Dan replies ✅ approved (Jesse facilitates and nudges if stuck). SLA: 72 hours per gate (full-feature flow only — change requests run the simplified 5-step flow with no biz gates). If no response, PM escalates and the ticket can move forward conditionally. Step 7 is a Dev + Ming design review (≤30 min sync) so the engineer fully understands the design and requirements before coding. Step 11 UAT Ready is the queue state between UAT pass and Biz & Ops Validation pickup. New Status options to add: BRD (high-level), BRD Final, Prototype, Sign-off · Design + Copy, Design Review, QA, UAT Ready, Biz & Ops Validation. New custom field on Bug Tracking: Found in.

⚡ Hard Rules
  1. UAT Status only flips when the change is deployed to the UAT environment. Engineers must not flip Status → QA from a local branch. QA must not flip QA → UAT until they've verified on the UAT env. Each handoff carries a comment — engineer → QA logs spec/AC + what changed; QA → UAT logs "covered X, didn't cover Y".
  2. Gates 5 and 12 — if the 72h SLA is breached, the pre-determined timeline must be adjusted. Jesse escalates to PM (Jeff) at the 72h mark. Jeff either fast-tracks approval via WhatsApp or pushes the launch date with the team. Don't silently let the deadline slip — visibility is the whole point of the SLA.
Step 7 · Design Review (≤30 min sync): engineer + Ming meet so the engineer fully understands the design and requirements before coding. Engineer walks through the design, raises edge cases / unclear interactions; Ming confirms intent. Ticket flips to Development after the meeting.
Biz & Ops gates (5 and 12) — approval mechanics:
  • Entry trigger: whoever flips the Status into the gate also @-mentions @Sam @Dan @Jesse in the same comment (Yves at gate 5; Ming at UAT Ready feeding gate 12).
  • Approval: Sam or Dan replies ✅ approved on the ticket — only one of them is needed.
  • Status moves forward after the approval comment: gate 5 → Ready For Development; gate 12 → Launch Ready.
  • Jesse facilitates: tracks pending reviews each morning, nudges Sam/Dan in WhatsApp at the 48h mark, escalates to Jeff at 72h SLA. Change requests run the simplified 5-step flow and skip these gates entirely.
  • Issue raised instead of approval: reply ❌ blocked: [reason] → ticket flips to Bug Found, loops back.
🚨 Hotfix exception (P0 prod bugs): skip pre-dev gates entirely. Report in WhatsApp group → ticket created on Bug Tracking with Found in = Production, Severity = Blocker → straight to Development → fast-tracked QA → Biz & Ops Validation can be confirmed via WhatsApp reply (any one of Sam / Dan / Jesse).
Parked states (off main flow): Pendingawaiting external input Not a bugrejected after triage

Simplified flow — small change requests

The 14-step flow above is for full new features (e.g. Crowdfund Phase 2). For small change requests (copy tweaks, small UI fixes, config changes, internal-only updates), Ops/PM at Triage classifies the ticket and routes it through this lighter path — QA verification is the only gate. Skip Pre-Dev, Design Review, UAT, and Biz & Ops Validation entirely.

Triage classification rule: Items with significant UI/UX, brand-facing copy changes, or new business commitments → full 14-step flow. Items affecting only backend, internal tooling, dev-only config, or trivial UI changes (e.g. typo fix, padding tweak) → simplified 5-step flow. Ops/PM marks the classification at Triage; once classified small, the ticket only needs QA pass before Launch Ready.

Gate scope reference

Four gates total — one in Pre-Dev (gate 5), three in Test (gates 9, 10, 12). Each answers a different question. Overlap is intentional — complementary lenses, not duplicated effort.

Gate 5 · Sign-off · Design + Copy

Sam / Dan (Jesse facilitates) · pre-build · 72h SLA
"Is the Design + Copy right before we build it?"
Looking for
Final design matches the BRD intent. Copy on-brand (English + Chinese). No commitments to artists/partners that the implementation can't honor.
Out of scope
Functional concerns (no code yet). Net-new requirements (re-open BRD if scope grew).
Pass action
Sam or Dan replies ✅ approved. Status flips → Ready For Development. Issue → Bug Found back to Design.

Gate 9 · QA

[QA tester] · post-build
"Does this work as built?"
Looking for
Functional bugs, edge cases, regressions, cross-browser, broken API behavior, data validation, performance.
Out of scope
UX opinions, copy ideas. If noticed, leave a comment — don't return as Bug Found.
Pass action
Flip Status → UAT. Comment: "QA passed [date], covered X, didn't cover Y".

Gate 10 · UAT

Ming · runs after QA
"Does this make sense to a real user?"
Looking for
End-to-end user flow makes sense, no surprises in the journey, feels right. Chinese copy only — clarity, tone, accuracy.
Out of scope
Functional bugs (QA's job — bounce back via Bug Found). English copy (Biz & Ops Validation handles).
Pass action
Flip Status → UAT Ready. @-mention @Sam @Dan @Jesse in pass comment.

Gate 12 · Biz & Ops Validation

Sam / Dan (Jesse facilitates) · pre-launch · 72h SLA
"Does this serve the business and read right in English?"
Looking for
Matches what was sold to artist/partner. Pricing/packaging right. Doesn't break existing deals. English copy on-brand and accurate.
Out of scope
Functional/UX bugs (QA/UAT's job). Chinese copy (Ming's job). Net-new requirements (PM/BRD process).
Pass action
Sam or Dan replies ✅ approved. Status flips → Launch Ready. Issue → Bug Found.

⚙ Required fields when submitting a bug ticket
  • Title — short, specific (e.g. "Crowdfund · pledge button doesn't submit on Safari")
  • Found in — single-select: QA / UAT / Biz Validation / Production
  • Severity — Blocker / High / Medium / Low
  • Screenshot or video — visual evidence (UAT env URL or prod screenshot)
  • Steps to reproduce — numbered, deterministic
  • Linked feature ticket — use Asana task dependency if the bug came out of a feature in flight (so the feature is blocked from shipping until the bug is done)
  • Assignee — leave blank; Ops triages each morning to assign
⚙ Meanwhile, the parent feature ticket
Flips to Bug Found (blocked). Re-enters QA once all linked bug tickets reach Done. The bugs travel the same swimlane independently.
⚙ Found in — new single-select on Bug Tracking
QA UAT Biz Validation Production
Default = Production for Ops-promoted tickets. Unlocks gate-effectiveness metric: % of defects caught at each gate vs slipping to prod.

Daily rhythm — QA and UAT

[QA tester] · QA role

Morning
Open QA Queue saved view (Status = QA). Pull from top of priority list.
During the day
Run functional tests on UAT env. Move tickets QA → UAT (pass) or QA → Bug Found (fail, with steps + screenshot).
Goal
Nothing waits >24h in QA — drain the queue daily so Ming's UAT pipeline stays full but never blocked.

Ming · UAT role

Morning
Open UAT Queue saved view (Status = UAT). Only tickets that already passed QA appear here.
During the day
Verify user flow + Chinese copy. Move tickets UAT → UAT Ready (pass) or UAT → Bug Found (fail, with reproduction steps + screenshot). On pass, @-mention @Sam @Dan @Jesse for Biz & Ops Validation (English copy + business sign-off).
End of day
Post 3 lines to team channel: tested · found · blocked. Comment-only on tickets — never edit copy or design.

Sam / Dan / Jesse · Biz & Ops role

Morning batch
Pick up tickets queued at Sign-off · Design + Copy (gate 5 entry) and UAT Ready (gate 12 entry). Sam or Dan reviews and replies ✅ approved; the reviewer flips Status forward (gate 5 → Ready For Development; gate 12: UAT Ready → Biz & Ops Validation while reviewing → Launch Ready after approval).
SLA enforcement
Each gate has a 72-hour SLA from when the ticket enters the queue (full features only — change requests skip these gates). Jesse pings @Sam @Dan in WhatsApp at the 48h mark if no reply. At 72h, escalate to PM (Jeff) for conditional move-forward.
Weekly call
Review gate-effectiveness metrics, queue depth, any tickets that hit SLA escalation, and any unresolved disagreements between biz and dev.

端到端流程 — 4 個階段,兩道 biz & ops 把關

兩道 Biz & Ops gate 包住工程階段 — gate 5 把關 Design + Copy、gate 12 把關實作。核可規則:Sam 或 Dan 任一人回 ✅ approved 即可(Jesse 負責協調,如卡住則 nudge)。SLA:每道 gate 72 小時內必須回應(只適用完整功能流程;change request 走簡化 5-step 流程,沒有 biz gate)。沒回應則 PM 升級處理,工單可有條件先往前。Step 7 是 Dev + Ming 在開始寫程式前的設計 review(≤30 分鐘),讓工程師完全理解設計與需求後再動工。Step 11 UAT Ready 是 UAT 通過後、Biz & Ops Validation 還沒接手前的 queue 狀態。要新增的 Status 選項:BRD (high-level)、BRD Final、Prototype、Sign-off · Design + Copy、Design Review、QA、UAT Ready、Biz & Ops Validation。Bug Tracking 板要新增的自訂欄位:Found in。

⚡ 硬性規定
  1. UAT Status 只有在變更部署到 UAT 環境後才能翻。工程師不要從本地分支翻 Status → QA。QA 不要在 UAT 環境上沒驗證過就翻成 UAT。每次交接都要附留言 — 工程 → QA 寫明 spec/AC + 改了什麼;QA → UAT 寫明「測了什麼,沒測什麼」。
  2. Gate 5 與 12 — 如果卡到 72h SLA 沒有核可,原本訂好的時程就要調整。Jesse 在 72h 時升級給 PM (Jeff)。Jeff 用 WhatsApp 加速核可,或跟團隊一起把上線日期往後挪。不要讓 deadline 默默滑走 — 可見度就是 SLA 的重點。
Step 7 · Design Review(≤30 分鐘同步會議):工程師和 Ming 一起開會,讓工程師在開始寫程式前完全理解設計和需求。工程師逐步走過設計、提出邊界 case 和不清楚的互動;Ming 確認意圖。會議結束後翻成 Development。
Biz & Ops gates(5 與 12)— 核可機制:
  • 進入觸發:翻 Status 進入 gate 的人在同一則留言中 @-mention @Sam @Dan @Jesse(gate 5 是 Yves;gate 12 之前的 UAT Ready 是 Ming)。
  • 核可:Sam 或 Dan 任一人在工單回覆 ✅ approved — 不需兩人都回。
  • Status 往前走:gate 5 → Ready For Development;gate 12 → Launch Ready。
  • Jesse 協調:每天早上追蹤待審核的工單,48h 在 WhatsApp 提醒 Sam/Dan,72h SLA 過期則升級給 Jeff。Change request 走簡化 5-step 流程,完全跳過這兩道 gate。
  • 有問題改回意見:回 ❌ blocked: [原因] → 工單翻成 Bug Found 退回。
🚨 Hotfix 例外(P0 線上 bug):跳過所有 pre-dev gate。在 WhatsApp 群組回報 → 在 Bug Tracking 開工單,Found in = Production、Severity = Blocker → 直接進 Development → 加速 QA → Biz & Ops Validation 用 WhatsApp 回覆確認(Sam / Dan / Jesse 任一人)。
擱置狀態(不在主流程上): Pending等候外部回應 Not a bug分流後判定不是 bug
