The 10-state Status field — three test gates

QA is a new option to add to Asana (doesn't exist today). It sits between Development and UAT. Business Validation lives in comments + @-mentions only — no Status state needed. Bug Found is the only return path; everything else moves forward.

⚡ The Hard Rule
A ticket only enters UAT once it's deployed to the UAT environment.
Engineers must not flip Status → QA while the change is on a local branch. QA must not flip QA → UAT until they've personally verified on the UAT env. Each handoff requires a comment: engineer → QA includes spec/AC and what changed; QA → UAT includes "QA passed [date], covered X, didn't cover Y".
How Business Validation works (no Status state): When Ming flips UAT → Launch Ready, she @-mentions the biz reviewer in her pass comment: "UAT verified [date]. @Sam @Dan please confirm before deploy." Sam/Dan reply ✅ approved. Dev only deploys after seeing that comment. If Sam/Dan raise an issue, it becomes Bug Found and loops back to Development.
Parked states (off main flow): Pendingawaiting external input Not a bugrejected after triage

Three-gate scope reference

Each gate answers a different question. Overlap is intentional — these are complementary lenses, not duplicated effort.

1 · QA gate

[QA tester] · runs FIRST
"Does this work as built?"
Looking for
Functional bugs, edge cases, regressions, cross-browser issues, broken API behavior, data validation, performance.
Background needed
Some technical familiarity; can read specs and acceptance criteria.
Out of scope
UX opinions ("button is ugly"), copy ideas. If noticed, leave a comment — don't return as Bug Found.
Pass action
Flip Status → UAT. Comment: "QA passed [date], covered X, didn't cover Y".

2 · UAT gate

Ming · runs SECOND
"Does this make sense to a real user?"
Looking for
User flow makes sense end-to-end, copy is clear, no surprises in the journey, feels right.
Background needed
User empathy, designer's eye. Doesn't need to know how it's built.
Out of scope
Functional bugs (QA should have caught them — bounce back via Bug Found). Design/copy changes are comments only, never edits.
Pass action
Flip Status → Launch Ready. @-mention Sam/Dan in the pass comment.

3 · Business Validation

Sam / Dan · runs THIRD · no Status change
"Does this serve the business?"
Looking for
Does it match what was sold to the artist/partner? Pricing/packaging right? Anything that breaks an existing deal? Public-facing copy on-brand?
Background needed
Knowledge of artist/partner agreements and business commitments.
Out of scope
Functional or UX bugs (QA/UAT's job). Net-new requirements (those go through PM/BR process).
Pass action
Reply ✅ approved on the ticket. Dev only deploys after seeing this reply. Issue → flag as Bug Found.

Daily rhythm — QA and UAT

[QA tester] · QA role

Morning
Open QA Queue saved view (Status = QA). Pull from top of priority list.
During the day
Run functional tests on UAT env. Move tickets QA → UAT (pass) or QA → Bug Found (fail, with steps + screenshot).
Goal
Nothing waits >24h in QA — drain the queue daily so Ming's UAT pipeline stays full but never blocked.

Ming · UAT role

Morning
Open UAT Queue saved view (Status = UAT). Only tickets that already passed QA appear here.
During the day
Move tickets UAT → Launch Ready (pass) or UAT → Bug Found (fail, with reproduction steps + screenshot).
End of day
Post 3 lines to team channel: tested · found · blocked. Comment-only on tickets — never edit copy or design.

Kill list — what to retire

Asana fields/options to delete or hide

  • Status options: Done, Fixed, Discussion, Design Review, Copywriting — replace with the 9-state flow above. Copywriting is already covered by the existing Type field.
  • Custom fields: Copy of Priority, Priority -, Task Progress — duplicates of Priority / Status.
  • Stale section "UAT April 27 - 28, 12PM (on test env)" on Bug Tracking — tickets are stranded there. Replace with date sections on the Bug Release Plan board.
