⚠ The problem we're solving

Why a single fixed target breaks the waitlist refill

Today's UAT has one number: Funding Target = $20,000. The campaign is "successful" only if exactly that amount is collected. The trouble starts during recovery — when some captures fail and we try to swap in waitlisters to make up the difference, the waitlisters' tier choices rarely add up to exactly the gap. Result: we either fall short of the target (failed campaign) or overshoot it (we collected more than we said we'd raise). Neither is acceptable today, which is why BR-31 has been trying to require amount-matching on waitlister replacement — a rule that's painful to enforce in practice and produces awkward queue states.

✗ Today · Fixed $20,000 target

1,000 backers × $20 = $20,000

1
End date hits, batch capture runs. 50 captures fail (cards expired, insufficient funds, 3DS timeouts). collected = $19,000.
2
Pull 50 waitlisters in FIFO to backfill. But the waitlist is a mix of tiers — some pledged $20, some $50, some $200.
3
If we pull the next 50 FIFO and they total $1,400: collected = $20,400 — over target, we now owe $400 we never said we'd collect.
4
If we hand-pick 50 that total exactly $1,000: ops becomes a manual amount-matching puzzle. Doesn't scale, breaks FIFO, fans complain about queue jumping.
Stuck: hit target exactly OR break FIFO fairness OR overshoot.
✓ Range model · $18,000–$20,000

Same 1,000 backers × $20, success defined as ≥ $18K

1
End date hits, batch capture runs. 50 captures fail identically. collected = $19,000. We're already past the $18K success line.
2
Pull waitlisters in pure FIFO — no amount-matching needed. Each new capture adds to collected.
3
Buffer = max − min = $2,000. As long as collected ≤ $20,000, any total inside the band is a valid finish.
4
Skip-overshoot guard (BR-N4): if the next waitlister's pledge would push collected > $20,000, skip them and try the next in queue.
Lands anywhere in $18K–$20K = Successful. No amount-match, FIFO preserved, no overshoot.
Takeaway: the (max − min) band is a tolerance window for the recovery phase. It converts an impossible exact-match problem into a simple FIFO walk with one bounds check. BR-31 simplifies. BR-32 becomes mechanical. And the BR-N5 smallest-tier cap ensures at least one tier always fits in the remaining headroom.

New BRs at a glance What this wireframe implements

BR-N2
Campaign goal as min/max range
Replace single goalUsd with minGoalUsd + maxGoalUsd. Locked at publish. Min = success threshold, max = displayed/hard cap.
BR-N3
Pre-end-date Goal Achieved + hard cap
Auto-flip to Goal Achieved when raised ≥ minGoalUsd. Hard cap at maxGoalUsd → batch capture fires (BR-28).
BR-N4
FIFO waitlist refill (amount-agnostic)
When captures fail, pull next waitlister in FIFO. Buffer absorbs amount mismatch. Skip waitlisters whose pledge would push collected > maxGoalUsd.
BR-N5
Smallest tier ≤ 50% of buffer
At least one viable "filler" tier must exist for refill. Formula: smallest tier price ≤ (max − min) × 0.5. Single-tier campaigns: rule applies to that one tier.

Implementation note for dev

pricePerShare stays a derived field, but the source changes: pricePerShare = maxGoalUsd / totalShares.

The old minShares field is no longer entered by the creator — it becomes a derived debug-only number: implicitMinShares = totalShares × (minGoalUsd / maxGoalUsd). Keep in admin debug view for audit, drop from public surfaces.

All references to "Funding Target" in stored copy / emails / contracts (BR-C1 / BR-C2) need a sweep — replace with "Goal range" or "Minimum goal" depending on context.
