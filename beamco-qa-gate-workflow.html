QA Gate Sub-Workflow — Triage, Routing, Closure

How QA/UAT tickets flow from intake to closure · 2026-05-07
PM Triage
Lane A · Bug
Lane B · UI/UX needs design input
Lane C · Change Request (out of scope)
QA Re-test
Fixed · Closed

Entry — three direct paths by ticket type

Tickets route by type. Most go straight to Dev or Designer — only tickets that need a real decision (suspected CRs, or design escalations) reach PM Triage.

REPORTER
QA / UAT Tester
files ticket · self-classifies type at filing
→
routes by type
BUG Lane A · directly to Dev — no decision needed, no PM involvement
UI/UX Lane B · directly to Designer — design input needed; designer handles or escalates
SUSPECTED CR Lane C · PM Triage queue — scope decision needed (Pass / Schedule / Defer)
Lane C is handled by Jeff in a daily session — escalated to Biz & Ops if needed. Outcomes: Pass (route to Lane A/B) · Schedule (target version) · Defer (backlog). If the lane is wrong, the next person re-routes — no PM step needed.

Three lanes — by what the next person decides

Each lane is defined by what the next person needs to do: just fix it (Bug → Dev), provide design input (UI/UX → Designer), or make a scope decision (CR → PM Triage). Tickets only enter Lane C when a real decision is needed.

Lane B · design handoff
Experience the issue on the live site first, then update the design.
  • Run the tester's steps on UAT/staging — real context tends to surface things static frames don't.
  • Drop the updated Figma frame in the Asana comment; a screenshot is fine for small changes.

Closure, re-open, and visibility

Closure ownership

Only the original tester closes the ticket — after re-testing the fix on UAT. Dev and Designer mark Ready For Re-test; tester moves to Fixed.

Re-open rule

If re-test fails, the same ticket reopens — don't spawn a new one. A reopen counter increments on the ticket. ≥2 reopens = quality signal, surface in retro.

Spec format (Lane B)

Designer delivers a Figma frame (link in Asana comment) for substantive changes; screenshot is OK for trivial tweaks. Always pin the source so dev doesn't re-litigate.

Tester visibility

Original reporter is auto-added as Asana collaborator on every ticket they raise — so they see status changes, comments, and re-test prompts without manual @-mentions.

Asana settings to enable this flow

  • Type field on Bug Tracking: Bug · Change Request — tester picks at filing; lane routing is determined by assignee (Designer = Lane B, Dev = Lane A, Jeff = Lane C). If the lane is wrong, the next person re-routes — no PM step needed.
  • Priority field: existing field reused — no new severity scale needed.
  • Auto-collaborator rule: when a ticket is created, the reporter is added as a collaborator and stays subscribed across all status changes.

QA Gate 子流程 — 分流、路由、結案

QA / UAT ticket 從進件到結案的流程 · 2026-05-07
PM 分流
Lane A · Bug
Lane B · UI/UX 需設計介入
Lane C · 變更需求（超出原範圍）
QA 重測
Fixed · 結案

進件 — 依類型直接分三路

測試人員依類型分流。大多數 ticket 直接走 Dev 或 Designer，不經過 PM。只有需要決策的（疑似 CR 或設計師升級）才進到 PM 分流。

REPORTER · 提單者
QA / UAT 測試人員
提單時自行分類 · 附步驟、截圖、環境
→
依類型分流
BUG Lane A · 直接給工程師 — 不需決策，PM 不介入
UI/UX Lane B · 直接給設計師 — 需設計輸入；設計師處理或升級
疑似變更需求 Lane C · PM 分流佇列 — 需範圍決策（Pass / Schedule / Defer）
Lane C 由 Jeff 處理，每日清一次決策佇列；必要時升級給 Biz & Ops。三個結果： Pass（轉 Lane A 或 B）· Schedule（標版本後 park）· Defer（backlog）。 Lane 標錯時下一個人自行轉手，不需 PM 介入。

三個 Lane — 依「下一個人要做什麼」

每個 lane 對應「下一個人需要做什麼」：直接修（Bug → 工程師）、提供設計輸入（UI/UX → 設計師）、做範圍決策（CR → PM 分流）。只有真的需要決策時，ticket 才會進到 Lane C。

Lane B · 設計交付
先到實際網站體驗一次，再更新設計。
  • 在 UAT/staging 上跑測試人員的步驟，真實情境裡常會看到靜態 frame 看不到的東西。
  • 更新後的 Figma frame 貼到 Asana 留言；小改動用 截圖 也好。

結案、重開、可見度

結案歸屬

只有原提單測試人員能 close ticket — 在 UAT 重測通過後。Dev 與設計師標 可重測；測試人員才能標 Fixed。

重開規則

重測失敗時，同一張單重開 — 不要開新單。重開計數 +1。≥2 次重開就是品質訊號，列入 retro 討論。

規格格式（Lane B）

實質改動由設計師交付 Figma frame（連結貼 Asana 留言）；微調可用 截圖。永遠把來源釘住，避免 Dev 來回確認。

測試人員可見度

原提單者自動加為 Asana collaborator，整張單的所有狀態變更、留言、重測通知都看得到，不需手動 @mention。

Asana 設定 — 啟用此流程

  • Type 欄位 在 Bug Tracking：Bug · 變更需求 — 測試人員提單時選；lane 路由依 assignee 決定（設計師 = Lane B、工程師 = Lane A、Jeff = Lane C）。lane 標錯時下一個人自行轉手，不需 PM 介入。
  • Priority 欄位：沿用既有欄位，不需要新增 severity。
  • 自動 collaborator 規則：建立 ticket 時自動把 reporter 加為 collaborator，整個生命週期保持訂閱。
