Date: 2026-05-27 · Prepared by Claude Solution Architect · Status: Reporting / Identity-Auth / Crowdfund all LOCKED

Direction change (the trigger for this doc)

August deliverable for Content Studio shifted:

  • Creator Studio Phase 1 = eShop → eShop deferred
  • August = Content Studio reporting module only (3 reports, below)

Service-layer features still in scope for the 2.0 push:

  • Migrate Ztor Simple-Version crowdfund into Beamco crowdfund — one crowdfund service serving two brands
  • Unified user DB — Ztor 2.0 SSO; 2.0 is system-of-record for identity (Ztor users + Beamco creators + Beamco fans); legacy brand DBs run in parallel, phased out later
  • Wire creator reporting data into 2.0 infra

Part 1 — Reporting Architecture LOCKED

The reframe

"Reporting module" is not a UI project. It is a read-model on top of a cross-brand creator spine: canonical identity + a unified earnings record. Reporting is the spine's first consumer. Resource the plumbing, not the screens.

The three reports (top-down from what a creator sees)

Report 1 — Crowdfund Project Progress (project-level, operational). Goal, raised, backers, % funded, milestone/fund-release status. Reads directly from the crowdfund service's own campaign state. All escrow + milestone-release machinery lives inside the crowdfund service and only surfaces here.

Report 2 — Creator Earnings (the aggregation surface). Sums realized earnings across { merch, event, affiliation, ip, crowdfund, film }. Crowdfund appears here only as released earnings — when a milestone fires, the crowdfund service emits one earning event. The escrow lifecycle never crosses into this report.

Report 3 — Film (content-performance POV). Film stats (views, watch-time, completion) from the Ztor VOD source ⊕ the film's earning line, read from the same earnings store rows Report 2 uses (source_type='film'). Film earning is recorded once; Report 2 aggregates it, Report 3 slices it and dresses it with stats. No number can disagree with itself.

Two data shapes (not one grand ledger)

1. Earnings event store — single source of money truth. One lean row per realized earning:

{ creator_id, brand,
  source_type: "merch"|"event"|"affiliation"|"ip"|"crowdfund"|"film",
  gross, fees, net, currency,
  occurred_at,
  ref }   // order / campaign / title id — for drill-down

No fund_state / milestone_ref / escrow fields — that complexity stays in the crowdfund service.

2. Crowdfund campaign state — read directly from the crowdfund service for Report 1.

Crowdfund money model (why escrow stays out of the earnings store)

Pledged money is not creator earnings. It is held at the project level in escrow and released by milestone:

  • Milestone 1 — payment fully collected → release 80%
  • Milestone 2 — released on Spotify → release 20%

Only the released tranches become crowdfund earning events in the store.

Decisions locked

  • Reporting is a consumer of the spine, not the deliverable itself.
  • Identity-authoritative + data-read-model (see Part 2).
  • Contract over schema: lock the earnings contract early; source schemas can churn until mid-July; only the thin ETL adapter waits for the lock.
  • Single source of truth for money: earnings recorded once, reports are views.

Part 2 — Unified User DB + Auth Service LOCKED

Split the problem

  • Identity & Auth — who you are, login, canonical user_id. Authoritative, real-time, 2.0-owned. August-critical.
  • User data — profiles, history, fan records. Eventually-consistent read-model synced from legacy. Deferred.

Ztor 2.0 SSO

  • A brand-aware platform IdP — one shared user base across brands, not tenant-isolated — built by the Beamco team, powering Ztor + Beamco now and Bookyay later. (Not "Beamco SSO".)
  • RS256 JWT + Redis sessions. Canonical user_id = token subject.

Canonical user model

  • One canonical user, with brand-scoped roles — e.g. user X → {beamco: creator, ztor: fan}. Per-brand, not global (Bookyay drops in cleanly; supports per-brand bans).
  • Three populations migrated: Ztor users (no native creator role), Beamco fans, Beamco creators. Creators are single-origin (Beamco) — removes the cross-brand creator entity-resolution problem.

Credentials & migration

  • OTP / magic-link at cutover — no password hashes migrated. Optional password-set post-login. Removes password reconciliation from the migration window.
  • Email is the identity key.

Account linking (BUILD in August, surfaced in Creator Studio)

  • Creator Studio is the cross-brand surface — the "two profiles, which one?" ambiguity bites there, so linking UX lives there.
  • Linking ≠ data merge. Linking writes an identity-graph edge (beamco acct ⇄ ztor acct = one canonical_user_id); reporting aggregates by canonical_user_id. Profile data stays per-brand, deferred.
  • Proof of ownership required — auto-suggest on email match, but always require an OTP/login challenge to the second account before writing the edge.
  • Build generically, expose in Creator Studio for August — consumer-wide linking reuses it later.
  • Don't gate the common case — single-identity creators walk straight in; detected-but-unlinked → logged-in identity + non-blocking nudge.

Ztor content → creator link (Topic C)

Ztor back-office links Beamco creators (visible via the 2.0 user DB) to Ztor films. Requires back-office read access to canonical creator identities + an ops owner for the mapping. Prerequisite for the Film report and the film line in Creator Earnings.

Auth-feature placement

Authentication → IdP (centralized). Authorization → brand.

  • IdP: social SSO (Google/FB/Apple — brokered), forgot-password (brand-skinned emails), MFA, email verification, session revocation, rate-limit/bot, global identity ban.
  • Brand: brand-level ban (authz — IdP validates identity; brand denies access), content moderation, role gating.
  • Cross-cutting: account deletion / GDPR export — name an owner.
  • Implications: IdP is a cross-brand SPOF → needs HA; per-brand theming is a hard requirement.
Open (delegated to dev) — build IdP from scratch vs Keycloak / Ory / Auth0 / Cognito. Recommendation: don't reimplement OAuth — use an existing IdP, spend custom effort on the linking flow + canonical-user migration.

Part 3 — Crowdfund Service Migration LOCKED

Base & migration

  • Base = Beamco crowdfund, generalized into the 2.0 crowdfund service. Ztor simple-version absorbed + retired (not ported).
  • Strangler migration — new campaigns on the unified service; existing campaigns drain on their current path. In-flight escrow never moves.

Payment — brand-level + aggregator (resolves the escrow/legal risk)

Crowdfund service  →  orchestrates: campaign state, pledges, milestone triggers, refund decisions (what)
Payment aggregator →  moves money: routes charge/refund/release to brand PSP, owns retry (how)
Brand PSP/merchant →  holds custody: each brand keeps its own merchant account, escrow, settlement
  • Money never sits in 2.0 infra — each brand's PSP holds funds; 2.0 only issues instructions. Largely answers the escrow-custody / money-transmitter question.
  • 80/20 milestone release = crowdfund service detects milestone → instructs aggregator → brand PSP executes payout.
  • Aggregator owns retry + refund (not per-brand) — keeps adapters thin. Ztor 1.17 refund-flow + payment-retry lands here, built once.

August crowdfund scope = adapters (+ two riders)

  • Adapters (the bulk) — per brand: branding/locale/currency, payment routing → aggregator, fan-tier/milestone config, notifications, frontend wiring.
  • Payment aggregator — new service.
  • Add brand-awareness to the core — Beamco base is single-brand; add a brand attribute + per-brand config. Lighter than multi-tenancy.

Brand-aware core — guidance for dev (delegated)

Brand-awareness, NOT multi-tenancy. Ztor + Beamco converge into 2.0, so brand is transitional metadata, not a permanent isolation boundary. Don't build tenant isolation you'll tear out.

  • Add a brand attribute on campaigns/pledges — do it now while in dev (cheaper than retrofitting).
  • Per-brand config — branding, payment routing, currency, fan-tier/milestone rules.
  • Filter by brand only where the UX needs it. Cross-brand reads are wanted (reporting) — no hard isolation layer.
  • Be exact on the money path — campaign brand must route funds to the correct brand PSP; wrong brand = money to the wrong merchant account.

Sequencing

  • Beamco fans-site rebuild (July) = build Beamco's crowdfund side on 2.0 infra — same pattern as the Ztor 2.0 redesign already underway. Turns the "AI exercise" into the real consolidation.
  • Reporting wiring is free — the core emits released-earnings events regardless of brand; reporting just reads them.
Open for dev — scope of adding brand-awareness to the Beamco core (brand attribute + per-brand config).

第一部分 — 報表架構 已定案

重新定義

「報表模組」不是一個 UI 專案。它是建立在跨品牌創作者骨幹之上的讀取模型：標準身分 + 統一收益紀錄。報表是骨幹的第一個消費者。要投資底層管線，而非畫面。

三份報表（由創作者所見由上而下定義）

報表 1 — 募資專案進度（專案層級、營運導向）。目標、已募金額、贊助人數、達成率、里程碑與撥款狀態。直接讀取 crowdfund 服務本身的活動狀態。所有 escrow + 里程碑撥款機制都留在 crowdfund 服務內，僅在此呈現。

報表 2 — 創作者收益（彙整面）。彙總 { merch, event, affiliation, ip, crowdfund, film } 的已實現收益。募資在此僅以「已撥付收益」出現——里程碑觸發時，crowdfund 服務發出一筆收益事件。escrow 生命週期絕不進入此報表。

報表 3 — 影片（內容成效視角）。來自 Ztor VOD 的影片數據（觀看數、觀看時長、完播率）⊕ 影片收益項目，讀取的是與報表 2 相同的 earnings store 紀錄（source_type='film'）。影片收益只記錄一次；報表 2 彙總、報表 3 切片並加上數據。沒有任何數字會自相矛盾。

兩種資料形態（而非單一大帳本）

1. Earnings event store — 金額的唯一真實來源。每筆已實現收益一列精簡紀錄：

{ creator_id, brand,
  source_type: "merch"|"event"|"affiliation"|"ip"|"crowdfund"|"film",
  gross, fees, net, currency,
  occurred_at,
  ref }   // 訂單 / 活動 / 影片 id — 供下鑽

沒有 fund_state / milestone_ref / escrow 欄位——那些複雜度留在 crowdfund 服務。

2. Crowdfund 活動狀態 — 報表 1 直接讀取 crowdfund 服務。

募資金流模型（為何 escrow 不進 earnings store）

已贊助的金額不是創作者收益。它在專案層級以 escrow 持有，並依里程碑撥款：

  • 里程碑 1 — 款項全數收齊 → 撥付 80%
  • 里程碑 2 — 於 Spotify 上架 → 撥付 20%

只有已撥付的款項才會成為 store 中的 crowdfund 收益事件。

已定案決策

  • 報表是骨幹的消費者，而非交付物本身。
  • 身分權威 + 資料讀取模型（見第二部分）。

  • 金額唯一真實來源：收益只記錄一次，報表是視圖。

第二部分 — 統一 User DB + 驗證服務 已定案

拆解問題

  • 身分與驗證 — 你是誰、登入、標準 user_id。權威、即時、2.0 擁有。八月關鍵。
  • 使用者資料 — 個人檔案、歷史、粉絲紀錄。由舊系統同步的最終一致讀取模型。延後。

Ztor 2.0 SSO

  • 一個品牌感知的平台 IdP — 跨品牌共用一份使用者基底、非租戶隔離 — 由 Beamco 團隊建置，現支援 Ztor + Beamco，未來 Bookyay。（不是「Beamco SSO」。）
  • RS256 JWT + Redis session。標準 user_id = token subject。

標準使用者模型

  • 單一標準使用者，搭配品牌範圍角色 — 例如 user X → {beamco: creator, ztor: fan}。依品牌而非全域（Bookyay 可乾淨接入；支援各品牌封鎖）。
  • 遷移三類人群：Ztor 用戶（無原生 creator 角色）、Beamco 粉絲、Beamco 創作者。創作者單一來源（Beamco）——消除跨品牌創作者的身分比對問題。

憑證與遷移

  • 切換時採 OTP / magic-link — 不遷移任何密碼雜湊。登入後可選擇設定密碼。把密碼對帳移出遷移視窗。
  • Email 為身分鍵。

帳號連結（八月建置，於 Creator Studio 露出）

  • Creator Studio 是跨品牌的介面——「兩個檔案、要哪個？」的模糊性在此浮現，故連結 UX 放這裡。
  • 連結 ≠ 資料合併。連結寫入一條身分圖譜邊（beamco 帳號 ⇄ ztor 帳號 = 同一 canonical_user_id）；報表依 canonical_user_id 彙整。檔案資料維持各品牌獨立、延後。
  • 需所有權驗證 — email 相符時自動建議，但寫入連結邊前一律要求對第二個帳號做 OTP/登入挑戰。
  • 機制通用化、八月只在 Creator Studio 露出 — 全站消費者連結之後沿用。
  • 別卡住常見情況 — 單一身分的創作者直接進入；偵測到但未連結 → 載入已登入身分 + 非阻斷式提示。

Ztor 內容 → 創作者連結（主題 C）

Ztor 後台把 Beamco 創作者（透過 2.0 user DB 可見）連到 Ztor 影片。需要後台對標準創作者身分的讀取權 + 一位維運負責人做對應。是影片報表與創作者收益中影片項目的前置條件。

驗證功能歸屬

驗證 → IdP（集中）。授權 → 品牌。

  • IdP：社交登入（Google/FB/Apple — 由 IdP 代理）、忘記密碼（品牌樣式信件）、MFA、email 驗證、session 撤銷、限流/防爬、全域身分封鎖。
  • 品牌：品牌層級封鎖（屬授權 — IdP 仍驗證身分；品牌拒絕存取）、內容審核、角色管控。
  • 橫切：帳號刪除 / GDPR 匯出 — 須指定負責人。
  • 影響：IdP 成為跨品牌單點故障 → 需高可用；各品牌樣式為硬性需求。
待決（交付開發團隊）— IdP 從零自建 vs Keycloak / Ory / Auth0 / Cognito。建議：別重寫 OAuth — 採用現成 IdP，把自訂工時花在連結流程 + 標準使用者遷移。

第三部分 — 募資服務遷移 已定案

基底與遷移

  • 基底 = Beamco crowdfund，泛化為 2.0 募資服務。Ztor 簡易版併入並淘汰（不移植）。
  • 絞殺者式遷移 — 新活動走統一服務；既有活動在現有路徑跑完。進行中的 escrow 絕不搬移。

金流 — 品牌層級 + 聚合器（解除 escrow/法務風險）

Crowdfund 服務   →  編排：活動狀態、贊助、里程碑觸發、退款決策（做什麼）
Payment 聚合器   →  搬錢：把扣款/退款/撥付路由到品牌 PSP，負責重試（怎麼做）
品牌 PSP/金流商  →  持有資金：各品牌保留自己的商戶帳號、escrow、清算
  • 金流絕不停留在 2.0 — 各品牌 PSP 持有資金；2.0 只下指令。大致解答了 escrow 保管 / 金流業者的問題。
  • 80/20 里程碑撥款 = crowdfund 服務偵測里程碑 → 指示聚合器 → 品牌 PSP 執行撥付。
  • 聚合器負責重試 + 退款（非各品牌各做）— 讓轉接層保持輕薄。Ztor 1.17 退款流程 + 金流重試集中於此，只做一次。

八月募資範圍 = 轉接層（+ 兩項附帶）

  • 轉接層（主體） — 各品牌：品牌樣式/語系/幣別、金流路由 → 聚合器、fan-tier/里程碑設定、通知、前端接線。
  • Payment 聚合器 — 新服務。
  • 為核心加入品牌感知 — Beamco 基底為單品牌；加品牌屬性 + 各品牌設定。比多租戶輕量。

品牌感知核心 — 給開發的指引（已交付）

是品牌感知，不是多租戶。Ztor + Beamco 會收斂進 2.0，所以品牌是過渡性中繼資料，而非永久隔離邊界。別建之後要拆掉的租戶隔離。

  • 在 campaigns/pledges 等加 brand 屬性 — 趁現在仍在開發時做（比事後補上便宜）。
  • 各品牌設定 — 品牌樣式、金流路由、幣別、fan-tier/里程碑規則。
  • 只在 UX 需要處依品牌過濾。跨品牌讀取是被期望的（報表）— 不做硬隔離層。
  • 金流路徑要精確 — 活動的品牌必須把資金路由到正確的品牌 PSP；品牌錯了 = 錢進錯商戶帳號。
